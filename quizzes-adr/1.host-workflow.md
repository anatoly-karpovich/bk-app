# 1. Context

После рефакторинга обработки чата backend использует последовательный pipeline:

```text
Raw Chat
→ Parser
→ Candidate Filter
→ Deduplicator
→ Persistence
→ Read Model
→ Ranker
```

Обработка сообщений отделена от UI и находится под контролем backend.

При этом workflow проведения викторины остаётся построенным вокруг внутренней state machine приложения.

Текущая модель проведения использует:

```text
draft
→ active
⇄ paused
→ completed / cancelled
```

Текущая модель вопроса использует:

```text
pending
→ active
→ completed

pending
→ skipped
→ pending
```

Дополнительно проведение хранит:

```ts
currentQuestionId: string | null;
```

Ведущий вынужден выполнять действия, необходимые не для проведения игры, а для переходов внутренней модели:

- начать проведение;
- поставить проведение на паузу;
- продолжить проведение;
- начать вопрос;
- завершить вопрос;
- пропустить вопрос;
- восстановить вопрос;
- дождаться автоматического запуска следующего вопроса.

Эта модель предполагает, что приложение управляет последовательным сценарием проведения.

В реальности ведущий должен иметь возможность:

1. открыть любой подготовленный вопрос;
2. скопировать готовое сообщение с вопросом;
3. провести вопрос в чате;
4. вставить чат;
5. удалить неправильные ответы;
6. при необходимости выбрать другое сообщение игрока;
7. увидеть рассчитанный результат;
8. скопировать сообщение с правильным ответом;
9. перейти к любому следующему вопросу;
10. вернуться к ранее проведённому вопросу и исправить результат.

Ведущий также может:

- подготовить больше вопросов, чем будет проведено;
- изменить порядок вопросов во время проведения;
- не использовать часть подготовленных вопросов;
- исправить результат уже проведённого вопроса;
- завершить проведение, даже если использованы не все вопросы.

Следовательно, порядок вопросов в исходной викторине и порядок их фактического проведения являются разными понятиями.

---

# 2. Problem statement

Текущий workflow оптимизирует внутреннюю согласованность state machine, но ухудшает работу ведущего.

Основные проблемы:

- обязательные lifecycle-действия не имеют самостоятельной ценности для пользователя;
- переход к вопросу связан с backend-состоянием;
- одновременно может существовать только один `active` вопрос;
- завершение вопроса обязательно для перехода дальше;
- приложение автоматически выбирает следующий вопрос;
- исходный `questionIndex` используется как порядок проведения;
- запасные вопросы требуют формального `skip`;
- ведущий не может свободно менять фактическую последовательность вопросов;
- статус вопроса смешивает несколько независимых фактов:
  - был ли вопрос проведён;
  - проверен ли его текущий результат;
  - открыт ли он сейчас на UI.

В результате приложение требует больше действий, чем проведение викторины с использованием обычного текстового редактора.

---

# 3. Decision drivers

Решение основывается на следующих приоритетах.

## 3.1 Минимум обязательных действий

Ведущий не должен выполнять действие исключительно для продвижения внутренней state machine.

> Если действие существует только потому, что приложению нужен внутренний state transition, такое действие должно быть удалено.

## 3.2 Свободная навигация

Ведущий может открыть любой вопрос в любой момент.

Навигация не является доменной операцией и не изменяет проведение на backend.

## 3.3 Отсутствие автоматического управления ведущим

Приложение не должно:

- автоматически запускать вопросы;
- автоматически переходить к другому вопросу без явного действия ведущего;
- блокировать переход из-за незавершённого lifecycle;
- требовать использования всех подготовленных вопросов.

## 3.4 Обратимость

Частые действия ведущего должны быть обратимыми и не должны требовать подтверждений.

## 3.5 Backend как источник истины

Backend остаётся единственным источником истины для:

- persisted-состояния проведения;
- проведённых вопросов;
- отметок проверки;
- порядка фактического проведения;
- выбранных ответов;
- рейтинга;
- наград;
- итоговой ведомости.

Frontend отвечает только за:

- выбранный в интерфейсе вопрос;
- локальное состояние элементов UI;
- отображение backend read model.

## 3.6 Разделение исходной структуры и фактического проведения

Необходимо различать:

```text
questionIndex
```

Исходный номер вопроса в snapshot викторины.

И:

```text
conductedOrder
```

Фактический номер вопроса в проведённой игре.

---

# 4. Decision

Проведение викторины моделируется как свободно редактируемая рабочая область ведущего, а не как последовательная state machine.

Ведущий может открыть любой вопрос, изменить его данные и перейти к другому вопросу без предварительного запуска или завершения текущего вопроса.

Домен хранит результаты работы ведущего, но не управляет его навигацией.

---

# 5. Event lifecycle

## 5.1 Новые статусы

Проведение имеет только два состояния:

```ts
type QuizEventStatus = "open" | "completed";
```

## 5.2 Создание проведения

После создания проведение сразу получает статус:

```text
open
```

Промежуточный `draft` отсутствует.

Сущность `Quiz` уже выполняет роль подготовленного и редактируемого шаблона викторины. Создание дополнительного draft-состояния внутри `QuizEvent` не даёт самостоятельной пользовательской ценности.

Workflow создания:

```text
Quiz
→ Create Quiz Event
→ Open Quiz Event
```

После создания ведущий сразу может:

- открыть любой вопрос;
- скопировать вопрос;
- импортировать чат;
- обрабатывать ответы;
- переходить между вопросами.

Отдельная операция `start event` отсутствует.

## 5.3 Завершение проведения

Ведущий может завершить `open` проведение:

```text
open
→ completed
```

`completed` означает:

- ведущий считает проведение законченным;
- проведение отображается в архиве;
- проведение становится read-only;
- итоговая ведомость считается финальной на текущий момент.

Завершение не требует:

- проведения всех подготовленных вопросов;
- review всех проведённых вопросов;
- отсутствия вопросов, требующих повторной проверки.

Перед завершением UI показывает фактическое состояние, например:

```text
Проведено: 10
Проверено: 9
Подготовлено: 15
```

Наличие непроведённых или непроверенных вопросов не блокирует завершение.

Поскольку завершение является редкой глобальной операцией, UI может запросить подтверждение.

## 5.4 Переоткрытие

Завершённое проведение можно явно переоткрыть:

```text
completed
→ open
```

После переоткрытия проведение снова становится редактируемым.

`reopen` является архивным действием и не входит в основной workflow проведения.

## 5.5 Удаляемые статусы и действия

Удаляются event statuses:

```text
draft
active
paused
cancelled
```

Удаляются event actions:

```text
start
pause
resume
cancel
```

Удаляется:

```ts
currentQuestionId: string | null;
```

# 6. Question lifecycle

У вопроса отсутствует lifecycle state.

Удаляются статусы:

```text
pending
active
completed
skipped
```

Удаляются действия:

```text
startQuestion()
completeQuestion()
skipQuestion()
restoreQuestion()
```

Удаляется автоматический запуск следующего вопроса.

Вместо lifecycle вопрос хранит два независимых факта:

```ts
interface QuizEventQuestion {
  conductedOrder: number | null;

  reviewedAt: string | null;
  reviewedByUserId: string | null;
}
```

---

# 7. Conducted question

## 7.1 Определение

Вопрос считается фактически проведённым, если ему присвоен:

```ts
conductedOrder: number;
```

Если:

```ts
conductedOrder === null;
```

вопрос считается ещё не проведённым.

## 7.2 Семантика

`conductedOrder` показывает место вопроса в фактической последовательности игры.

Пример:

```text
Исходная викторина:
1, 2, 3, 4, 5

Фактически проведено:
1 → 3 → 5 → 2
```

Persisted-модель:

```text
Quiz question 1 → conductedOrder 1
Quiz question 3 → conductedOrder 2
Quiz question 5 → conductedOrder 3
Quiz question 2 → conductedOrder 4
Quiz question 4 → conductedOrder null
```

## 7.3 Присвоение порядка

При первом завершении обработки непроведённого вопроса backend присваивает:

```ts
conductedOrder =
  max(existing conductedOrder) + 1;
```

Переход к вопросу через sidebar или URL сам по себе не присваивает `conductedOrder`.

Копирование текста вопроса или правильного ответа также не присваивает `conductedOrder`.

## 7.4 Стабильность порядка

После присвоения `conductedOrder` сохраняется при:

- повторном открытии вопроса;
- изменении чата;
- изменении выбранных ответов;
- сбросе `reviewed`;
- повторной проверке результата.

Исправление результата уже проведённого вопроса не должно менять его место в фактической последовательности игры.

## 7.5 Отмена факта проведения

Для защиты от случайного нажатия доступно отдельное secondary action:

```text
Считать вопрос непроведённым
```

Операция:

- очищает `conductedOrder`;
- очищает `reviewedAt`;
- очищает `reviewedByUserId`;
- перенумеровывает последующие проведённые вопросы без разрывов;
- инициирует пересчёт данных, зависящих от фактического порядка.

Поскольку операция может изменить бонусные позиции и награды, она требует подтверждения.

Операция не является частью обычного workflow и не должна отображаться как primary action.

## 7.6 Ручная перестановка проведённых вопросов

Drag-and-drop и прямое редактирование `conductedOrder` в первой версии не поддерживаются.

Фактический порядок формируется последовательностью действий ведущего.

Необходимость полноценного reorder должна подтверждаться отдельным пользовательским требованием.

# 8. Reviewed question

## 8.1 Определение

`reviewed` означает:

> Ведущий считает обработку текущего результата вопроса законченной на данный момент.

Это не означает:

- что вопрос невозможно изменить;
- что результат окончательно заморожен;
- что ведущий обязан перейти к следующему вопросу;
- что вопрос нельзя повторно открыть;
- что вопрос невозможно перепроверить.

## 8.2 Persisted representation

```ts
reviewedAt: string | null;
reviewedByUserId: string | null;
```

Если `reviewedAt !== null`, текущий результат считается проверенным.

Если `reviewedAt === null`, вопрос:

- ещё не проверялся;
- либо требует повторной проверки после изменения.

## 8.3 Установка отметки

В основном workflow отдельная кнопка «Отметить обработанным» не используется.

Primary action называется:

```text
К следующему вопросу
```

Операция атомарно:

1. отмечает текущий вопрос как reviewed;
2. присваивает `conductedOrder`, если вопрос ещё не был проведён;
3. сохраняет обновлённое проведение;
4. открывает следующий непроведённый вопрос.

Если непроведённых вопросов больше нет, primary action меняется на:

```text
Завершить обработку
```

В этом случае вопрос отмечается reviewed, но автоматического завершения всего проведения не происходит.

## 8.4 Свободная навигация

Открытие другого вопроса через навигацию:

- не отмечает текущий вопрос reviewed;
- не присваивает `conductedOrder`;
- не изменяет backend;
- не требует подтверждения.

Ведущий может покинуть текущий вопрос в любой момент.

## 8.5 Сброс reviewed

Если после review изменяются persisted-данные, способные повлиять на результат вопроса, отметка сбрасывается:

```ts
reviewedAt = null;
reviewedByUserId = null;
```

К таким изменениям относятся:

- изменение effective chat;
- добавление новых effective messages;
- полная замена чата;
- исключение игрока;
- возврат игрока;
- выбор другого сообщения игрока;
- иное изменение selected answers;
- изменение данных, влияющих на ranking или awards.

Сброс reviewed:

- не меняет `conductedOrder`;
- не открывает другой вопрос;
- не инициирует автоматическую навигацию.

Вопрос отображается как:

```text
Проведён · требует повторной проверки
```

Действия, не влияющие на persisted-результат, reviewed не сбрасывают:

- открытие вопроса;
- копирование текста;
- локальное раскрытие или сворачивание UI;
- навигация;
- повторный импорт, не изменивший effective state.

Точная семантика effective mutations определяется отдельными ADR.

# 9. Navigation model

## 9.1 Selected question

Выбранный вопрос является UI state, а не состоянием `QuizEvent`.

Backend не хранит:

```ts
currentQuestionId;
```

Рекомендованный route:

```text
/quizzes/events/:eventId/questions/:questionId
```

При открытии проведения frontend выбирает вопрос в следующем порядке:

```text
questionId из URL
→ последний выбранный вопрос из local storage
→ первый непроведённый вопрос
→ первый вопрос
```

Хранение последнего вопроса в local storage является UI convenience и не влияет на доменную модель.

## 9.2 Свободный выбор

Ведущий может открыть:

- любой непроведённый вопрос;
- любой проведённый вопрос;
- вопрос, требующий повторной проверки;
- вопрос, отличный от следующего по исходному номеру.

Backend-команды всегда содержат явный:

```ts
questionId;
```

Backend не проверяет, какой вопрос открыт на UI.

## 9.3 Primary next action

После обработки текущего вопроса кнопка «К следующему вопросу» открывает первый вопрос, у которого:

```ts
conductedOrder === null;
```

Следующим считается **непроведённый**, а не просто `unreviewed` вопрос.

Уже проведённый вопрос с очищенным reviewed не должен автоматически становиться следующим вопросом эфира.

## 9.4 Previously conducted questions requiring review

Проведённые вопросы с:

```ts
conductedOrder !== null;
reviewedAt === null;
```

отображаются отдельно как требующие повторной проверки.

Они не участвуют в автоматическом выборе следующего непроведённого вопроса.

## 9.5 Автоматические переходы

Отсутствуют автоматические переходы после:

- импорта чата;
- изменения ответа;
- копирования вопроса;
- копирования правильного ответа;
- сброса reviewed;
- открытия вопроса;
- завершения проведения.

Единственный переход, инициируемый primary action, происходит после явного клика:

```text
К следующему вопросу
```

# 10. Question ordering in UI

Навигация разделяется на две группы.

## 10.1 Проведённые вопросы

Проведённые вопросы отображаются первыми и сортируются по:

```ts
conductedOrder;
```

Пример:

```text
Проведены — 3

#1  Вопрос 1   Проверен
#2  Вопрос 3   Проверен
#3  Вопрос 5   Требует проверки
```

## 10.2 Непроведённые вопросы

Непроведённые вопросы отображаются после проведённых и сортируются по исходному:

```ts
questionIndex;
```

Пример:

```text
Ещё не проведены — 12

Вопрос 2
Вопрос 4
Вопрос 6
```

## 10.3 Исходный номер вопроса

`questionIndex` остаётся неизменяемым идентификатором позиции вопроса в snapshot викторины.

Он используется для:

- отображения исходного номера;
- связи с вопросом из Quiz;
- вопрос-специфичных шаблонов;
- правил, относящихся к конкретному подготовленному вопросу.

Свободная навигация не изменяет `questionIndex`.

# 11. Prepared questions and unused questions

Ведущий может подготовить больше вопросов, чем будет проведено.

Например:

```text
Подготовлено: 15
Проведено: 10
```

Оставшиеся пять вопросов не требуют:

- статуса `skipped`;
- ручного исключения;
- формального завершения;
- обработки перед завершением event.

Вопрос с:

```ts
conductedOrder === null;
```

просто не участвовал в проведении.

Награды и итоговая статистика учитывают только фактически проведённые вопросы.

Точная связь `conductedOrder` с reward rules определяется ADR о наградах.

---

# 12. Progress model

Основные показатели:

```text
Проведено
Проверено
Подготовлено
```

Пример header:

```text
Проведено 8 · Проверено 7 · Подготовлено 15
```

Основной progress indicator:

```text
Проверено 7 из 8 проведённых
```

Непроведённые запасные вопросы не должны создавать впечатление, что проведение обязательно не закончено.

Lifecycle labels вопросов не отображаются:

```text
Ожидает
В эфире
Завершён
Пропущен
```

Вместо них используются понятные ведущему признаки:

```text
Проведён #N
Проверен
Требует проверки
Ещё не проведён
```

---

# 13. Clipboard actions

Копирование вопроса и правильного ответа является UI interaction.

Backend не сохраняет:

```text
questionCopiedAt
answerCopiedAt
copiedByUserId
```

Копирование:

- не запускает вопрос;
- не присваивает `conductedOrder`;
- не устанавливает reviewed;
- не влияет на ranking;
- не влияет на навигацию.

После успешного копирования UI локально меняет состояние кнопки, например:

```text
Копировать
→ Скопировано
```

Не требуется snackbar или модальное окно.

---

# 14. Permissions

Сохраняется текущая ownership model.

Редактировать проведение могут:

- host проведения;
- admin.

Остальные авторизованные пользователи проекта могут иметь read-only доступ согласно существующей authorization policy.

Выбранный вопрос является локальным для каждого пользователя.

Просмотр или навигация одного пользователя не меняет экран другого.

---

# 15. Concurrent editing

Полноценное совместное realtime-редактирование одного проведения не поддерживается.

Предполагается один логический редактор.

Для защиты от одновременных изменений из:

- нескольких вкладок;
- host и admin;
- устаревшего frontend state,

backend должен использовать optimistic concurrency.

Конкретная реализация может использовать:

```ts
version: number;
```

или эквивалентный revision mechanism.

При конфликте backend не должен молча перезаписывать более свежие данные.

Точная concurrency implementation находится вне scope данного ADR.

---

# 16. Confirmations

Частые, локальные и обратимые действия не требуют подтверждения.

Без подтверждения выполняются:

- открытие вопроса;
- навигация;
- «К следующему вопросу»;
- завершение обработки последнего вопроса;
- копирование;
- изменение selected answer;
- исключение и возврат игрока;
- обычные операции с чатом, если они обратимы и не destructive.

Подтверждение допускается для редких действий с широкими последствиями:

- завершение проведения;
- удаление проведения;
- отмена факта проведения вопроса;
- destructive chat replacement, если это будет предусмотрено ADR о chat mutations.

---

# 17. Delete action

Удаление проведения не отображается как основное действие рабочего экрана.

Оно размещается:

- в secondary menu;
- либо на странице списка проведений.

Удаление требует подтверждения.

Удаление не является частью normal host workflow.

---

# 18. Read model requirements

Read model проведения должен позволять frontend без дополнительной бизнес-логики определить:

- проведён ли вопрос;
- его фактический номер;
- проверен ли его текущий результат;
- требует ли он повторной проверки;
- какой вопрос является первым непроведённым;
- количество проведённых вопросов;
- количество проверенных вопросов;
- количество подготовленных вопросов.

Минимально question view должен содержать:

```ts
interface QuizEventQuestionView {
  id: string;

  questionIndex: number;
  conductedOrder: number | null;

  reviewedAt: string | null;
  reviewedByUserId: string | null;
}
```

Derived state:

```ts
const isConducted = conductedOrder !== null;
const isReviewed = reviewedAt !== null;
const needsReview = isConducted && !isReviewed;
```

Event view должен предоставлять или позволять однозначно вычислить:

```ts
conductedQuestionsCount;
reviewedQuestionsCount;
preparedQuestionsCount;
```

---

# 19. Command model

Минимальные workflow-команды:

## Event

```text
create
complete
reopen
delete
```

## Question

```text
reviewAndContinue
unreview
markAsNotConducted
```

`reviewAndContinue` является application-level use case.

Он должен атомарно:

1. загрузить event;
2. проверить, что event находится в `open`;
3. установить reviewed;
4. присвоить `conductedOrder`, если его ещё нет;
5. сохранить event;
6. вернуть обновлённый read model.

Выбор следующего вопроса может выполняться frontend на основании обновлённого read model либо возвращаться как navigation hint.

Backend не должен хранить выбранный frontend-вопрос.

---

# 20. Removed backend behavior

Из текущего `QuizEventEngine` удаляются:

```text
start()
pause()
resume()
cancel()

startQuestion()
completeQuestion()
skipQuestion()
restoreQuestion()
reorder()
```

Удаляется automatic next question.

Удаляются проверки:

```text
только active event
только active question
уже есть активный вопрос
этот вопрос не активен
все вопросы должны быть completed или skipped
```

Вместо них mutating commands проверяют только:

- event существует;
- пользователь имеет право редактирования;
- event находится в `open`;
- question принадлежит event;
- command-specific invariants соблюдены.

# 21. Removed frontend behavior

Удаляются:

```text
Начать проведение
Пауза
Продолжить
Начать вопрос
Завершить вопрос
Пропустить
Восстановить
```

Удаляются chips:

```text
Черновик
В эфире
Пауза
Ожидает
Активен
Пропущен
Завершён
```

Удаляется автоматическая привязка selected question к:

```ts
event.currentQuestionId;
```

Основная рабочая область строится вокруг текущего выбранного вопроса и свободной навигации.

# 22. Invariants

После реализации решения должны выполняться следующие инварианты.

## Event invariants

1. Новое проведение создаётся сразу в статусе `open`.
2. Только `open` event можно изменять.
3. `completed` event является read-only.
4. `completed` event можно переоткрыть.
5. Для завершения не требуется проведение всех подготовленных вопросов.
6. Для завершения не требуется review всех проведённых вопросов.
7. Event не хранит выбранный на UI вопрос.

## Question invariants

1. У вопроса отсутствует lifecycle status.
2. Один вопрос имеет не более одного `conductedOrder`.
3. Два проведённых вопроса не могут иметь одинаковый `conductedOrder`.
4. `conductedOrder` образует непрерывную последовательность от `1` до количества проведённых вопросов.
5. Изменение результата проведённого вопроса не меняет его `conductedOrder`.
6. Вопрос может быть проведённым и одновременно требовать повторной проверки.
7. Непроведённый вопрос не участвует в итогах проведения.
8. Навигация не изменяет вопрос.
9. Копирование не изменяет вопрос.
10. `questionIndex` не меняется во время проведения.

## Review invariants

1. Review является обратимой отметкой.
2. Review не блокирует последующее редактирование.
3. Effective mutation результата сбрасывает review.
4. Сброс review не изменяет `conductedOrder`.
5. Сброс review не инициирует навигацию.

# 23. Rejected alternatives

## 23.1 Сохранить существующую state machine

Отклонено, потому что:

- добавляет обязательные действия;
- связывает навигацию с backend;
- не соответствует реальной работе ведущего;
- усложняет backend и frontend;
- требует искусственных `skip` для запасных вопросов.

## 23.2 Хранить только reviewed без conductedOrder

Отклонено, потому что reviewed описывает проверку результата, а не фактический порядок проведения.

После изменения reviewed-вопроса отметка может быть сброшена, но вопрос не перестаёт быть фактически проведённым.

## 23.3 Определять порядок только по reviewedAt

Отклонено, потому что:

- повторный review может изменить timestamp;
- исправление результата не должно менять историческое место вопроса;
- бизнес-правила не должны зависеть от сортировки технических timestamps;
- `conductedOrder` выражает бизнес-смысл явно.

## 23.4 Использовать questionIndex как порядок проведения

Отклонено, потому что ведущий может проводить вопросы в произвольном порядке.

`questionIndex` принадлежит структуре Quiz snapshot, а не фактическому событию.

## 23.5 Автоматически отмечать вопрос при переходе через sidebar

Отклонено, потому что открытие другого вопроса не означает завершение обработки текущего.

## 23.6 Требовать review всех вопросов перед завершением

Отклонено, потому что:

- часть вопросов может быть запасной;
- review является progress marker;
- запрет возвращает обязательный lifecycle transition.

## 23.7 Полностью отказаться от completed

Отклонено, потому что completed нужен для:

- архива;
- защиты финального результата от случайных изменений;
- отделения текущих проведений от законченных.

---

# 24. Consequences

## Positive

- основной workflow ведущего становится короче;
- удаляются обязательные lifecycle-кнопки;
- ведущий может менять порядок проведения;
- запасные вопросы не требуют обработки;
- отсутствуют автоматические переходы;
- вопрос можно исправить после проведения без изменения его места;
- доменная модель явно разделяет исходный и фактический порядок;
- frontend больше не синхронизирует навигацию через backend;
- `QuizEventEngine` становится существенно меньше;
- уменьшается количество status-dependent условий;
- UX лучше соответствует проведению игры в реальном времени.

## Negative

- появляется новое persisted-поле `conductedOrder`;
- требуется корректная перенумерация при отмене факта проведения;
- reward calculation должен различать `questionIndex` и `conductedOrder`;
- возникает отдельное состояние «проведён, но требует проверки»;
- frontend navigation становится немного сложнее визуально;
- требуется optimistic concurrency или иной revision mechanism.

## Accepted trade-off

Дополнительная модель `conductedOrder + reviewed` сложнее одной галочки, но она устраняет смешение двух разных бизнес-фактов:

- вопрос был проведён;
- текущий результат вопроса был проверен.

Это усложнение считается оправданным, поскольку фактический порядок влияет на награды и итог проведения.

---

# 25. Migration outline

Точная migration strategy определяется отдельно во время реализации.

Предварительное соответствие текущей и новой модели:

```text
QuizEventStatus:
draft / active / paused → open
completed              → completed
cancelled              → удалить или мигрировать отдельно
```

```text
QuizEventQuestionStatus:
completed → conductedOrder по completedAt/start order
active    → решение миграции вручную или по startedAt
pending   → conductedOrder null
skipped   → conductedOrder null
```

Для существующих данных необходимо отдельно решить:

- как восстановить фактический порядок;
- можно ли считать `completedAt` надёжным источником порядка;
- сохранять ли cancelled events;
- как мигрировать awards, завязанные на старый `questionIndex`.

До production deployment миграция должна быть покрыта отдельными тестами.

---

# 26. Out of scope

Данный ADR не определяет:

- append/replace semantics;
- message identity;
- восстановление selected answers после replace;
- player answer selection model;
- stable award resolution;
- конкретную модель ranking anchor;
- порядок сообщений при переходе через полночь;
- точные reward source keys;
- API payloads chat operations;
- UI карточек игроков;
- правила расчёта наград после изменения conducted order;
- realtime collaborative editing.

Эти решения оформляются отдельными ADR.

---

# 27. Final principle

> Проведение викторины является рабочей областью ведущего, а не последовательностью обязательных состояний приложения.

Приложение сохраняет факты:

- какие вопросы были проведены;
- в каком порядке они были проведены;
- какие результаты проверены;
- какие результаты требуют повторной проверки.

Но приложение не управляет тем, какой вопрос ведущий обязан открыть следующим.
