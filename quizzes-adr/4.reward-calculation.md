# ADR — Quiz Reward Calculation and Result Finalization

## Status

**Proposed**

## Related decisions

- `ADR — Quiz Chat Processing`
- `ADR — Quiz Host Workflow`
- `ADR — Quiz Chat Mutation Model`
- `ADR — Quiz Player Answer Selection Model`
- `ADR — Quiz Ranking and Time Ordering` — planned

---

# 1. Context

Quiz event хранит:

- snapshot исходной викторины;
- snapshot reward configuration;
- подготовленные вопросы;
- фактический порядок проведения;
- сохранённые выбранные ответы;
- ranking;
- рассчитанные награды;
- итоговую ведомость.

После упрощения host workflow один вопрос может находиться в нескольких независимых состояниях:

```ts
conductedOrder: number | null;
reviewedAt: string | null;
reviewedByUserId: string | null;
```

`conductedOrder` означает, что вопрос был фактически проведён.

`reviewedAt` означает, что ведущий закончил обработку текущего результата вопроса.

До review ведущий может:

- добавлять и заменять чат;
- выбирать правильных игроков;
- менять selected message;
- несколько раз сохранять selection set;
- просматривать предварительный ranking.

Награды не должны рассчитываться при каждом промежуточном сохранении.

Они должны появляться только после явного завершения обработки вопроса.

---

# 2. Problem statement

Необходимо определить:

- когда вопрос начинает участвовать в итоговой ведомости;
- когда рассчитываются награды;
- какие reward rules используют исходный `questionIndex`;
- какие reward rules используют фактический `conductedOrder`;
- что происходит после изменения уже reviewed-вопроса;
- что происходит при изменении фактического порядка проведённых вопросов;
- нужно ли хранить рассчитанные награды;
- как строится промежуточная и финальная summary;
- как избежать расчёта наград в read model;
- как сохранить консистентность после compaction.

Текущая реализация пересчитывает awards внутри mutation logic и вызывает reward resolution повторно.

Это потенциально опасно для variable reward pools.

Однако для текущего quiz domain принимается более простая модель:

> Награды викторины являются детерминированными и полностью задаются reward configuration.

Следовательно, награды можно безопасно пересчитывать с нуля при изменении результата.

---

# 3. Decision drivers

## 3.1 Явный момент фиксации результата

Ведущий должен сам определить момент, когда результат вопроса считается обработанным.

Награды не должны появляться после каждого промежуточного Save.

## 3.2 Отсутствие лишней reward state machine

Не вводятся:

- pending awards;
- approved awards;
- reward entitlement ledger;
- dormant awards;
- reward reroll history;
- ручное подтверждение каждой награды.

## 3.3 Детерминированность

Для одинаковых:

- event snapshot;
- question;
- conducted order;
- ranking;
- reward rules

результат наград должен быть одинаковым.

## 3.4 Backend как источник истины

Frontend не рассчитывает награды.

Read model не вызывает reward calculation с side effects.

## 3.5 Snapshot stability

Reward rules созданного event берутся только из event snapshot.

Изменение исходного Quiz или Config не влияет на уже созданное проведение.

---

# 4. Decision

Награды вопроса рассчитываются в момент review.

Основной workflow action:

```text
К следующему вопросу
```

атомарно:

1. проверяет, что event находится в `open`;
2. проверяет наличие сохранённого selection set;
3. присваивает `conductedOrder`, если вопрос ещё не был проведён;
4. устанавливает `reviewedAt`;
5. устанавливает `reviewedByUserId`;
6. рассчитывает награды по текущему ranking;
7. сохраняет awards;
8. обновляет summary;
9. возвращает обновлённый event read model.

Frontend после успешного ответа открывает следующий непроведённый вопрос.

Если непроведённых вопросов больше нет, аналогичная команда завершает обработку текущего вопроса без автоматического завершения event.

---

# 5. Question result phases

## 5.1 Draft result

До review вопрос может иметь:

- effective chat;
- persisted selected answers;
- authoritative ranking;
- `conductedOrder === null`;
- `reviewedAt === null`;
- пустой awards array.

Такой результат является предварительным.

UI показывает:

```text
Предварительный результат
```

Он не участвует в общей наградной ведомости.

## 5.2 Reviewed result

После review вопрос имеет:

```ts
conductedOrder: number;
reviewedAt: string;
reviewedByUserId: string;
awards: QuizAward[];
```

Такой вопрос участвует в:

- player correct answer counters;
- regular rewards;
- bonus rewards;
- total rewards;
- event summary.

## 5.3 Conducted but unreviewed result

Если ранее reviewed-вопрос был изменён, он может иметь:

```ts
conductedOrder: number;
reviewedAt: null;
awards: [];
```

Это означает:

> Вопрос был фактически проведён, но его текущий результат требует повторной проверки.

Такой вопрос временно не участвует в наградной summary.

---

# 6. Reward rule coordinates

Необходимо различать две позиции вопроса.

## 6.1 Source question index

```ts
questionIndex: number;
```

Это номер вопроса в snapshot исходной Quiz.

Он используется для:

- связи с исходным question;
- question-specific regular reward override;
- message template override;
- других правил, относящихся к конкретному подготовленному вопросу.

## 6.2 Conducted order

```ts
conductedOrder: number;
```

Это фактический номер вопроса в проведённой игре.

Он используется для reward rules, зависящих от порядка проведения.

Пример:

```text
Quiz questions:
1, 2, 3, 4, 5

Проведены:
1 → 5 → 3
```

Результат:

```text
Quiz question 1 → conductedOrder 1
Quiz question 5 → conductedOrder 2
Quiz question 3 → conductedOrder 3
```

Бонус третьего проведённого вопроса применяется к исходному вопросу №3.

---

# 7. Regular reward rules

Regular reward rule определяется исходным вопросом.

Выбор effective rule:

```ts
regularRewardOverrides.find((override) => override.questionIndex === question.questionIndex)?.rule ??
  defaultRegularRule;
```

Regular reward rule не зависит от `conductedOrder`.

Поддерживаются существующие режимы:

```ts
type QuizRegularRewardRule = QuizAllAcceptedRewardRule | QuizPositionRewardRule;
```

## 7.1 All accepted

При:

```ts
mode: "all_accepted";
```

каждый игрок в текущем ranking получает прописанную reward configuration.

## 7.2 By position

При:

```ts
mode: "by_position";
```

награда определяется позицией игрока в текущем ranking.

Если для позиции rule отсутствует, regular award не создаётся.

---

# 8. Bonus reward rules

Bonus reward rule относится к фактической позиции вопроса в проведении.

Рекомендуемая модель:

```ts
interface QuizBonusRewardRule {
  id: string;

  conductedOrder: number;
  position: number;

  rewardPool: QuizRewardPool;
}
```

Поле:

```ts
questionIndex;
```

в bonus rule заменяется на:

```ts
conductedOrder;
```

Bonus rule применяется, если одновременно:

```text
question.conductedOrder === bonusRule.conductedOrder
```

и:

```text
rankedAnswer.position === bonusRule.position
```

Один игрок может одновременно получить:

- regular award;
- один или несколько bonus awards.

---

# 9. Deterministic reward policy

Для текущей версии quiz domain reward pools считаются детерминированными.

Конфигурация однозначно определяет итоговый набор ресурсов.

Не поддерживаются:

- случайный выбор одного варианта;
- weighted reward roll;
- reroll;
- случайная сумма;
- reward entropy;
- manual reward override.

`RewardGrantService.resolve()` либо заменяется pure deterministic calculation, либо используется только при гарантированно детерминированных pools.

## Invariant

> Повторный расчёт одного и того же результата обязан возвращать одинаковые rewards.

Если в будущем появятся случайные reward pools, потребуется отдельный ADR и отдельная persisted resolution model.

---

# 10. Award calculation

Award calculator получает:

```ts
interface QuizAwardCalculationInput {
  quizSnapshot: QuizSnapshot;
  eventQuestion: QuizEventQuestion;
  ranking: QuizRankedAnswer[];
}
```

Он использует:

- source `questionIndex`;
- actual `conductedOrder`;
- current ranking;
- event reward snapshot.

Результат:

```ts
interface QuizAward {
  id: string;

  playerName: string;
  selectedMessageId: string;

  questionIndex: number;
  conductedOrder: number;

  source: QuizAwardSource;

  rewards: ResourceAmount[];
}
```

`resolvedRewards` может быть переименовано в:

```ts
rewards;
```

поскольку отдельной random resolution phase больше нет.

---

# 11. Award source

```ts
interface QuizAwardSource {
  kind: "regular_all" | "regular_position" | "bonus_position";

  questionIndex: number;
  conductedOrder: number;

  position: number | null;

  regularRuleMode: QuizRegularRewardRule["mode"] | null;
  bonusRuleId: string | null;
}
```

`questionIndex` и `conductedOrder` сохраняются вместе для понятного аудита.

Для regular award source:

- `questionIndex` определяет применённый source question rule;
- `conductedOrder` сохраняет фактическое место вопроса.

Для bonus award source:

- `bonusRuleId` определяет rule;
- `conductedOrder` определяет фактический bonus slot.

---

# 12. Review action

## 12.1 Preconditions

Review разрешён, если:

- event имеет статус `open`;
- actor имеет право редактирования;
- question принадлежит event;
- selection draft был сохранён;
- persisted selections не содержат dangling references;
- ranking может быть построен.

Пустой selection set допустим.

Вопрос может быть reviewed без правильных ответов.

## 12.2 Atomic operation

Review mutation атомарно:

```text
assign conductedOrder if missing
→ set review metadata
→ calculate ranking
→ calculate awards
→ rebuild summary
→ save event
```

Если расчёт или persistence не удались, не меняются:

- conductedOrder;
- review metadata;
- awards;
- summary.

## 12.3 Re-review

Если вопрос уже имеет `conductedOrder`, повторный review:

- сохраняет существующий conductedOrder;
- рассчитывает awards заново;
- устанавливает новый reviewedAt;
- обновляет reviewedByUserId;
- перестраивает summary.

---

# 13. Changes after review

Если effective mutation способна изменить результат reviewed-вопроса, backend атомарно:

```ts
reviewedAt = null;
reviewedByUserId = null;
awards = [];
```

`conductedOrder` сохраняется.

К таким mutations относятся:

- effective append;
- effective replace;
- clear chat;
- effective selection Save;
- удаление dangling selection после replace.

После mutation:

- ranking может существовать;
- awards отсутствуют;
- вопрос не участвует в reward summary;
- UI показывает `Требует повторной проверки`.

Новый review заново рассчитывает awards по актуальному результату.

---

# 14. No-op mutations

Если mutation не изменила effective result:

- review сохраняется;
- awards сохраняются;
- summary сохраняется;
- повторный reward calculation не выполняется.

Примеры:

- append только duplicates;
- no-op replace;
- Save того же selection set;
- повторный выбор уже сохранённого результата.

---

# 15. Change of conducted order

`conductedOrder` может измениться при secondary action:

```text
Считать вопрос непроведённым
```

Операция:

1. очищает conductedOrder выбранного question;
2. очищает его review;
3. очищает его awards;
4. перенумеровывает последующие conducted questions;
5. пересчитывает bonus rewards затронутых reviewed-вопросов;
6. обновляет summary.

## 15.1 Regular rewards

Regular rewards не меняются из-за нового conductedOrder, поскольку зависят от source `questionIndex`.

Они могут быть пересозданы вместе с полной awards projection для простоты.

## 15.2 Bonus rewards

Bonus rewards пересчитываются по новым conducted orders.

Поскольку rewards детерминированы, автоматический пересчёт безопасен.

## 15.3 Reviewed state of affected questions

Для остальных reviewed-вопросов, чей conductedOrder изменился:

- review сохраняется;
- selected answers сохраняются;
- ranking сохраняется;
- awards автоматически пересчитываются;
- summary обновляется.

Повторная ручная проверка не требуется, поскольку content result не изменился.

## 15.4 Confirmation

Операция требует подтверждения, поскольку может изменить награды нескольких вопросов.

---

# 16. Mark question as not conducted

Для выбранного question:

```ts
conductedOrder = null;
reviewedAt = null;
reviewedByUserId = null;
awards = [];
```

Вопрос:

- перестаёт считаться проведённым;
- исключается из summary;
- остаётся доступным для повторного проведения;
- сохраняет chat и selected answers, если отдельное действие не очищает их.

Если позже он снова reviewed:

- получает новый последний conductedOrder;
- награды рассчитываются по новой фактической позиции.

---

# 17. Summary participation

В summary участвуют только вопросы:

```ts
conductedOrder !== null && reviewedAt !== null;
```

Проведённый, но unreviewed question:

- не увеличивает correct answer count;
- не добавляет rewards;
- не участвует в total selected answers итоговой ведомости;
- отображается как требующий проверки.

Prepared but not conducted questions также не участвуют.

---

# 18. Summary model

Рекомендуемые поля:

```ts
interface QuizEventSummary {
  players: QuizPlayerSummary[];

  totalPreparedQuestions: number;
  totalConductedQuestions: number;
  totalReviewedQuestions: number;

  totalSelectedAnswers: number;
  totalUniquePlayers: number;

  totalRewards: ResourceAmount[];

  generatedAt: string;
}
```

`completedQuestions` удаляется.

## 18.1 totalPreparedQuestions

Количество всех questions в event snapshot.

## 18.2 totalConductedQuestions

Количество questions:

```ts
conductedOrder !== null;
```

## 18.3 totalReviewedQuestions

Количество questions:

```ts
conductedOrder !== null && reviewedAt !== null;
```

## 18.4 totalSelectedAnswers

Количество selected answers только в reviewed conducted questions.

## 18.5 totalUniquePlayers

Количество уникальных игроков, присутствующих хотя бы в одном reviewed result.

---

# 19. Player summary

```ts
interface QuizPlayerSummary {
  playerName: string;

  correctAnswers: number;

  regularRewards: ResourceAmount[];
  bonusRewards: ResourceAmount[];
  totalRewards: ResourceAmount[];
}
```

`correctAnswers` равен количеству reviewed conducted questions, в которых player присутствует в selected answers.

Regular и bonus rewards агрегируются раздельно.

`totalRewards` является суммой обоих наборов.

---

# 20. Summary rebuilding

Summary является materialized projection.

Она полностью перестраивается после mutations, которые меняют:

- review state;
- awards;
- conductedOrder;
- selected answers reviewed-question;
- bonus slot assignment.

Используется pure calculator:

```ts
QuizEventSummaryCalculator;
```

Он не вызывает reward calculation и не создаёт side effects.

Он получает уже рассчитанные question awards.

---

# 21. Persistence

Question хранит awards как persisted snapshot:

```ts
interface QuizEventQuestion {
  awards: QuizAward[];
}
```

Хотя rewards детерминированы, persistence необходима для:

- фиксации результата проведения;
- независимости completed event от будущих изменений calculation code;
- быстрого read model;
- аудита;
- compaction;
- final answer snapshots;
- стабильной итоговой ведомости.

Awards не вычисляются заново при обычном read.

---

# 22. Complete event

При завершении event:

1. backend выполняет consistency validation;
2. пересобирает summary из persisted reviewed results;
3. не рассчитывает новые awards для unreviewed questions;
4. не делает implicit review;
5. не меняет conductedOrder;
6. сохраняет final summary;
7. переводит event в `completed`.

Завершение разрешено при наличии:

- непроведённых вопросов;
- conducted unreviewed questions.

UI показывает предупреждение:

```text
Проведено: 10
Проверено: 9
Один вопрос не участвует в итоговой ведомости
```

---

# 23. Reopen

При reopen:

- event снова становится `open`;
- existing awards сохраняются;
- existing summary сохраняется до следующей mutation;
- ничего не пересчитывается автоматически без причины;
- никакие награды не меняются от самого факта reopen.

Последующие effective mutations работают по обычным правилам:

```text
change result
→ clear review and awards
→ re-review
→ calculate again
```

---

# 24. Compaction

После retention и archival compaction сохраняются:

- final selected answer snapshots;
- persisted awards;
- final ranking;
- final summary;
- conductedOrder;
- review metadata;
- reward source metadata;
- event reward snapshot.

Удаляться могут:

- raw fragments;
- alternative unselected messages;
- parser diagnostics;
- temporary provenance.

Отдельный reward ledger не хранится.

Он не нужен при детерминированной reward model.

---

# 25. Read model

Question view должен позволять различать:

```ts
const isConducted = conductedOrder !== null;
const isReviewed = reviewedAt !== null;
const hasFinalRewards = isConducted && isReviewed;
```

До review UI показывает:

```text
Предварительный результат
```

После review:

```text
Результат вопроса
```

Если review сброшен:

```text
Проведён · требует повторной проверки
```

Awards отображаются только из persisted question awards.

Frontend не рассчитывает reward rules.

---

# 26. Backend components

Рекомендуется разделить:

```ts
QuizAwardCalculator;
QuizEventSummaryCalculator;
```

## 26.1 QuizAwardCalculator

Pure deterministic component.

Input:

```ts
quizSnapshot;
eventQuestion;
ranking;
```

Output:

```ts
QuizAward[];
```

Он:

- выбирает regular rule по questionIndex;
- выбирает bonus rules по conductedOrder;
- формирует awards;
- не читает repository;
- не изменяет event;
- не использует randomness.

## 26.2 QuizEventSummaryCalculator

Pure component.

Input:

```ts
eventQuestions;
resources;
```

Output:

```ts
QuizEventSummary;
```

Он использует только reviewed conducted questions и persisted awards.

## 26.3 QuizEventEngine

Engine координирует:

- review;
- unreview after mutations;
- conducted order;
- award calculation;
- summary rebuild.

Read model factory не вызывает calculators с side effects.

Review endpoint может быть application-level action:

```http
POST /projects/:projectId/quiz-events/:eventId/questions/:questionId/review
```

Payload:

```json
{
  "revision": 17
}
```

Response:

```ts
interface ReviewQuizQuestionResult {

  result: {
    conductedOrder: number;
    awardsCount: number;
    reviewedAt: string;
  };

```

Frontend интерпретирует успешный review как сигнал открыть следующий непроведённый question.

Backend не хранит выбранный UI question.

---

# 28. Atomicity

Mutations, затрагивающие rewards, являются атомарными.

Если не удалось:

- построить ranking;
- рассчитать rewards;
- пересобрать summary;
- пройти validation;
- сохранить event;
- пройти optimistic concurrency check,

не изменяются:

- conductedOrder;
- reviewed metadata;
- awards;
- summary.

---

# 29. Concurrency

Review и order-changing actions используют optimistic concurrency.

Устаревшая форма не должна review-вить вопрос поверх более свежего chat или selection state.

Review request должен ссылаться на актуальную revision.

При conflict:

- review не применяется;
- awards не рассчитываются;
- UI загружает актуальный question;
- ведущий повторно проверяет результат.

---

# 30. Invariants

## Reward invariants

1. Rewards детерминированы.
2. Reward calculation не использует randomness.
3. Один и тот же input создаёт одинаковые rewards.
4. Awards рассчитываются только при review или order reconciliation reviewed questions.
5. Read operation не рассчитывает awards.
6. Unreviewed question не имеет active awards.
7. No-op mutation не меняет awards.
8. Effective result change очищает awards.
9. Re-review полностью пересчитывает awards.
10. Manual reroll отсутствует.

## Question invariants

1. Question участвует в reward summary только если conducted и reviewed.
2. `questionIndex` определяет source-specific regular rule.
3. `conductedOrder` определяет bonus slot.
4. Изменение result не меняет conductedOrder.
5. Изменение conductedOrder автоматически пересчитывает bonus awards reviewed questions.
6. Пустой selected answer set является валидным reviewed result.
7. Один player может получить regular и bonus awards одновременно.

## Summary invariants

1. Summary строится только по reviewed conducted questions.
2. Summary использует persisted awards.
3. Summary не создаёт rewards.
4. Summary materialized после relevant mutations.
5. Completed event summary не включает unreviewed questions.
6. Reopen сам по себе не меняет summary.

---

# 31. Rejected alternatives

## 31.1 Calculate rewards on every Save

Отклонено, потому что Save selections является промежуточным действием проверки формы.

## 31.2 Calculate rewards on first conductedOrder assignment before review

Отклонено, потому что conductedOrder и review присваиваются в одной явной операции.

## 31.3 Include unreviewed conducted questions in reward summary

Отклонено.

Текущий результат вопроса не подтверждён ведущим и не должен участвовать в наградной ведомости.

## 31.4 Permanent reward resolution ledger

Отклонено как преждевременная универсальность.

Текущие quiz rewards детерминированы и безопасно пересчитываются.

## 31.5 Entitlement identity and dormant awards

Отклонено по той же причине.

## 31.6 Random reward pools

Не поддерживаются в текущем решении.

Их появление требует отдельного ADR.

## 31.7 Automatic fallback reward preservation

Отклонено.

Полный deterministic recalculation проще и прозрачнее.

## 31.8 Manual reroll

Отклонено.

## 31.9 Manual reward override

Отклонено для первой версии.

## 31.10 Calculate awards inside read model

Отклонено, потому что read operation не должна менять persisted domain state.

## 31.11 Use questionIndex for bonus slots

Отклонено, потому что ведущий может менять фактический порядок проведения.

## 31.12 Reset review for all questions after conducted reorder

Отклонено.

Если selections и ranking не изменились, deterministic bonus rewards можно безопасно пересчитать автоматически.

---

# 32. Consequences

## Positive

- reward model остаётся простой;
- отсутствует ledger;
- отсутствует reroll logic;
- нет pending/approved award states;
- награды появляются в понятный момент review;
- промежуточные Saves не создают награды;
- изменение результата полностью очищает старые awards;
- повторный review даёт актуальный результат;
- bonus rules учитывают реальный порядок проведения;
- completed event хранит persisted reward snapshot;
- read model не имеет side effects;
- summary всегда строится по подтверждённым вопросам.

## Negative

- unreviewed conducted question временно исчезает из reward summary;
- изменение reviewed-вопроса требует повторного review;
- order-changing action может пересчитать awards нескольких вопросов;
- reward configuration ограничена детерминированными pools;
- появление случайных наград потребует нового архитектурного решения;
- persisted awards дублируют вычисляемую projection.

## Accepted trade-off

Детерминированная модель сознательно ограничивает универсальность ради простоты.

Для текущих викторин это соответствует реальному продукту:

```text
reward rule
→ заранее прописанный набор ресурсов
```

Если домен изменится, random reward resolution будет добавлена отдельным решением, а не заранее встроена в основной workflow.

---

# 33. Migration outline

Текущие awards содержат:

```ts
resolvedRewards;
```

Предварительная migration:

```text
resolvedRewards → rewards
```

Необходимо:

1. убедиться, что используемые quiz reward pools детерминированы;
2. запретить variable pools в quiz config validation;
3. заменить bonus rule `questionIndex` на `conductedOrder`;
4. мигрировать существующие bonus rules;
5. удалить повторный resolve из selection mutations;
6. очищать awards при effective result mutations;
7. рассчитывать awards только в review action;
8. перестроить summary model;
9. удалить `completedQuestions`;
10. добавить totalConductedQuestions и totalReviewedQuestions;
11. покрыть migration и calculators unit tests.

Если существующие данные были рассчитаны случайным образом, их awards нужно сохранить как historical snapshot и не пересчитывать автоматически без отдельной migration policy.

---

# 34. Required tests

Минимальные scenarios:

## Review

- первый review присваивает conductedOrder;
- review создаёт regular awards;
- review создаёт bonus awards по conductedOrder;
- пустой ranking создаёт reviewed question без awards;
- re-review сохраняет conductedOrder;
- review rebuilds summary.

## Result mutation

- effective Save очищает review и awards;
- no-op Save сохраняет awards;
- effective append очищает review и awards;
- duplicate-only append сохраняет awards;
- replace pruning selection очищает awards;
- clear chat очищает awards.

## Ordering

- source question override использует questionIndex;
- bonus использует conductedOrder;
- нестандартный порядок вопросов назначает бонус правильному question;
- mark not conducted перенумеровывает questions;
- affected reviewed bonus awards пересчитываются;
- regular awards остаются корректными.

## Event lifecycle

- complete не review-вит вопросы автоматически;
- complete не включает unreviewed question в summary;
- reopen не пересчитывает awards;
- read model не вызывает reward calculation.

## Determinism

- одинаковый input создаёт одинаковые awards;
- quiz config rejects non-deterministic reward pools;
- repeated calculation has no side effects.

---

# 35. Out of scope

Данный ADR не определяет:

- random reward pools;
- weighted reward selection;
- manual reroll;
- manual reward override;
- reward entitlement ledger;
- reward history;
- external reward delivery;
- фактическую выдачу ресурсов игроку;
- rollback уже выданной внешней награды;
- ranking anchor через полночь;
- archival scheduler implementation.

---

# 36. Final principle

> Награда появляется тогда, когда ведущий завершил обработку вопроса.

До review существует предварительный ranking.

После review существует подтверждённый результат с наградами.

Если результат изменился, старые награды удаляются.

После повторного review они детерминированно рассчитываются заново.
