# ADR — Quiz Chat Mutation Model

## Status

**Proposed**

## Related decisions

- `ADR — Quiz Chat Processing`
- `ADR — Quiz Host Workflow`
- `ADR — Quiz Player Answer Selection Model`
- `ADR — Quiz Reward Stability` — planned
- `ADR — Quiz Ranking and Time Ordering` — planned

---

# 1. Context

Quiz backend обрабатывает вставленный ведущим чат через pipeline:

```text
Raw Chat
→ Parser
→ Candidate Filter
→ Canonical Identity
→ Deduplicator
→ Persistence
→ Read Model
```

После обработки backend хранит:

```ts
interface QuizEventQuestion {
  chatFragments: QuizChatFragment[];
  chatMessages: QuizChatMessage[];
}
```

Ведущему необходимы три операции над чатом вопроса:

```text
Append
Replace
Clear
```

Они должны поддерживать следующий workflow:

```text
ведущий вставляет фрагмент
→ backend парсит его
→ effective chat обновляется
→ frontend перестраивает локальную форму выбора ответов
→ ведущий продолжает редактирование
```

Chat mutation не должна автоматически сохранять выбранные правильные ответы.

Checkbox и radio выбора ответов находятся в локальном frontend draft и отправляются на backend только отдельной batch-командой, определённой в `ADR — Quiz Player Answer Selection Model`.

---

# 2. Problem statement

Необходимо однозначно определить:

- что является текущим effective chat вопроса;
- как работает append;
- как работает replace;
- как работает clear;
- что считается одним logical message;
- как дедуплицируются сообщения;
- как сохраняется порядок сообщений внутри одной минуты;
- какие message IDs сохраняются после replace;
- что происходит с persisted selections, если их messages исчезают;
- когда сбрасывается review вопроса;
- что видит ведущий после успешного импорта;
- как долго сохраняются raw fragments и alternative messages.

Без этих правил возможны непредсказуемые ситуации:

- повторная вставка создаёт дубликаты;
- одинаковое сообщение получает новый ID после replace;
- сообщения с одинаковым `HH:mm` меняются местами;
- persisted selection продолжает ссылаться на удалённое message;
- append требует промежуточного сохранения формы;
- frontend теряет понимание, какой чат backend реально использует;
- history fragments начинает неявно управлять active state.

---

# 3. Decision drivers

## 3.1 Простота workflow ведущего

Ведущий должен иметь возможность:

```text
вставить первый фрагмент
→ проверить сообщения
→ вставить ещё один фрагмент
→ продолжить проверку
```

Без промежуточного сохранения выбранных ответов.

## 3.2 Backend как источник истины для чата

Backend отвечает за:

- parsing;
- candidate filtering;
- canonical identity;
- deduplication;
- effective message set;
- ordering;
- persistence;
- player grouping read model.

Frontend не должен повторно парсить или дедуплицировать чат.

## 3.3 Frontend как владелец временной selection-формы

Chat mutation не должна:

- автоматически выбирать правильных игроков;
- автоматически сохранять radio;
- создавать persisted exclusion;
- отправлять отдельные player decisions;
- интерпретировать checkbox state.

Frontend после mutation самостоятельно merge-ит новый read model со своим несохранённым draft.

## 3.4 Предсказуемость

Append должен быть non-destructive.

Replace должен полностью определять новую effective версию чата.

Clear должен быть отдельным явным действием.

## 3.5 Точный порядок сообщений

Поскольку timestamp содержит только часы и минуты, backend обязан сохранять дополнительный порядок исходных строк.

## 3.6 Отсутствие event sourcing

Raw fragments являются history и diagnostic data, но active state не должен вычисляться replay всей истории при каждом чтении.

# 4. Decision

Текущий чат вопроса хранится как материализованное effective state:

```ts
chatMessages: QuizChatMessage[];
```

История операций хранится отдельно:

```ts
chatFragments: QuizChatFragment[];
```

`chatMessages` являются единственным источником истины для:

- player groups;
- available message options;
- ranking candidates;
- effective chat preview;
- последующих append/replace операций;
- backend validation selection batch request.

`chatFragments` являются временной audit/debug history.

Они не управляют active state и не replay-ятся при каждом чтении.

---

# 5. Effective chat state

## 5.1 Определение

Effective chat — текущий нормализованный и дедуплицированный набор сообщений вопроса.

В него входят только сообщения, которые:

1. успешно распознаны parser;
2. прошли candidate filter;
3. получили canonical identity;
4. не были отброшены как duplicates;
5. принадлежат текущей версии чата после append, replace или clear.

## 5.2 Persisted representation

```ts
interface QuizChatMessage {
  id: string;

  from: string;
  to: string[];
  text: string;
  timestamp: string | null;
  transport: ChatTransport;

  canonicalKey: string;

  sourceFragmentId: string;
  sourceLineNumber: number;

  effectiveOrder: number;
}
```

Конкретные названия полей могут быть скорректированы при реализации, но модель должна явно разделять:

- logical identity;
- provenance;
- effective ordering.

## 5.3 Active source of truth

Grouping, available radio options и ranking candidates строятся только по:

```ts
question.chatMessages;
```

Backend не replay-ит `chatFragments`.

## 5.4 Removed messages

Сообщения, удалённые replace или clear:

- не участвуют в read model;
- не участвуют в ranking;
- не доступны как radio options;
- не хранятся как `isActive: false` рядом с effective messages.

Historical raw data при этом может оставаться в fragment history до compaction.

# 6. Chat fragment history

## 6.1 Назначение

Fragment хранит:

- вставленный raw text;
- тип операции;
- пользователя;
- время;
- статистику parsing;
- результат mutation.

Fragment нужен во время проведения для:

- понимания того, что уже вставлялось;
- диагностики parser behavior;
- расследования неполного или ошибочного импорта;
- поддержки полного reopen до compaction.

## 6.2 Model

```ts
interface QuizChatFragment {
  id: string;
  mode: "append" | "replace";

  rawText: string;

  insertedAt: string;
  insertedByUserId: string;

  parsedMessagesCount: number;
  candidateMessagesCount: number;
  duplicateMessagesCount: number;

  previousMessagesCount: number;
  nextMessagesCount: number;

  addedMessagesCount: number;
  removedMessagesCount: number;
  retainedMessagesCount: number;

  effectiveChange: boolean;
}
```

Некоторые counts могут вычисляться динамически, если это упростит persistence.

## 6.3 Fragment history is not an editing model

В normal host workflow отсутствуют действия:

- активировать fragment;
- деактивировать fragment;
- удалить fragment из истории;
- выбрать набор активных fragments;
- вручную replay-ить историю.

Ведущий управляет effective chat только через:

```text
append
replace
clear
```

# 7. Canonical message identity

## 7.1 Назначение

Canonical identity отвечает на вопрос:

> Являются ли два распознанных сообщения одним logical message?

Она используется для:

- дедупликации внутри fragment;
- дедупликации append против effective chat;
- сопоставления старых и новых messages при replace;
- сохранения stable IDs;
- определения retained messages.

## 7.2 Identity fields

Canonical identity основывается на нормализованных значениях:

```text
transport
sender
recipients
text
timestamp
```

Концептуально:

```ts
canonicalKey = identityOf({
  transport,
  normalizedSender,
  normalizedRecipients,
  normalizedText,
  normalizedTimestamp,
});
```

Точная serialization или hashing implementation находится вне scope ADR.

## 7.3 Fields excluded from identity

В identity не входят:

```text
message UUID
fragment ID
sourceLineNumber
effectiveOrder
parser array index
first-seen metadata
```

Эти поля описывают положение и происхождение сообщения, а не его logical content.

## 7.4 Timestamp

Timestamp является частью identity, включая `null`.

```text
21:05 !== null
```

Одинаковый текст одного игрока с разными timestamp считается разными messages.

## 7.5 Transport

Сообщения из разных transports считаются разными:

```text
to !== private !== clan
```

## 7.6 Identical messages within one minute

Если один игрок отправил два сообщения с полностью одинаковыми identity fields в одну минуту:

```text
21:05 · private · Emrys · Минск
21:05 · private · Emrys · Минск
```

они считаются одним logical message.

Без секунд или platform message ID невозможно надёжно отличить реальный повтор от дубликата одного сообщения в нескольких вставках.

Это принимается как ограничение текущего chat source.

# 8. Normalization rules

## 8.1 Sender

Для nickname:

- удаляются внешние пробелы;
- display form сохраняется;
- регистр не меняется;
- identity остаётся case-sensitive.

```text
" Emrys " == "Emrys"
"Emrys" != "emrys"
```

Case-insensitive grouping не применяется без подтверждённого правила платформы.

## 8.2 Recipients

Recipients нормализуются детерминированно:

- trim;
- удаление duplicates;
- стабильный порядок, если исходный порядок не имеет бизнес-смысла.

Точная политика зависит от parser contract.

## 8.3 Text

Для identity:

- удаляются внешние пробелы;
- нормализуются line endings;
- технические повторные пробелы могут быть сведены к одному;
- регистр не меняется;
- punctuation не удаляется;
- semantic normalization не применяется.

```text
"Минск " == "Минск"
"Минск" != "минск"
"Минск" != "Минск?"
```

Parser и deduplicator не определяют правильность ответа.

# 9. Message ordering

## 9.1 Problem

Chat timestamp содержит только:

```text
HH:mm
```

За одну минуту может поступить несколько десятков сообщений.

Сортировка только по timestamp недостаточна.

## 9.2 Source order

Parser сохраняет:

```ts
sourceLineNumber: number;
```

`sourceLineNumber` отражает порядок сообщения внутри конкретного raw fragment.

Он не входит в identity, поскольку одно logical message может находиться на разных строках разных fragments.

## 9.3 Effective order

Backend хранит:

```ts
effectiveOrder: number;
```

Это стабильный secondary ordering key текущего effective chat.

Концептуальная сортировка:

```text
relative timestamp
→ effectiveOrder
```

Точная логика relative timestamp и перехода через полночь определяется отдельным ranking ADR.

## 9.4 Append order

При append:

- существующие messages сохраняют `effectiveOrder`;
- новые unique messages получают следующие значения;
- порядок новых messages соответствует порядку parser output;
- parser output должен сохранять порядок исходных строк.

Пример:

```ts
maxOrder + 1;
maxOrder + 2;
maxOrder + 3;
```

## 9.5 Replace order

Replace объявляет новый fragment полной актуальной версией чата.

После replace:

- retained и new messages получают новый `effectiveOrder`;
- order соответствует новому complete fragment;
- sourceLineNumber обновляется по новому fragment;
- stable message ID может сохраняться;
- старый effectiveOrder не сохраняется.

Stable identity не означает stable effective position.

# 10. Append mutation

## 10.1 Intent

Append используется для добавления новых кусков к уже собранному чату.

Типовые сценарии:

- первая вставка;
- дозагрузка продолжения;
- вставка пропущенного блока;
- продолжение после reload;
- добавление сообщений во время проверки формы.

## 10.2 Pipeline

```text
rawText
→ parse
→ candidate filter
→ canonical identity
→ deduplicate inside fragment
→ deduplicate against effective chat
→ append unique messages
→ rebuild effective read model
```

## 10.3 Invariant

> Append никогда не удаляет и не изменяет существующие effective messages.

Append:

- не меняет IDs existing messages;
- не меняет existing effectiveOrder;
- не заменяет provenance existing messages;
- только добавляет новые unique messages.

## 10.4 Deduplication

Append дедуплицирует:

1. внутри нового fragment;
2. против current effective chat.

При duplicate:

- existing message сохраняется;
- ID сохраняется;
- effectiveOrder сохраняется;
- duplicate учитывается в statistics;
- source fragment existing message не меняется.

## 10.5 No-op append

Если append не добавил unique messages:

```ts
effectiveChange = false;
```

Тогда:

- effective chat не меняется;
- reviewed не сбрасывается;
- persisted answer selections не меняются;
- fragment attempt может сохраняться;
- UI получает feedback, что новых messages нет.

## 10.6 Interaction with local selection draft

Append не требует промежуточного Save checkbox/radio формы.

После response frontend merge-ит новый read model со своим local draft:

- сохраняет существующие checkbox state;
- сохраняет radio, если message остаётся;
- добавляет новые messages;
- создаёт новые groups unchecked;
- выбирает первый radio нового group локально.

Эта логика принадлежит `ADR — Quiz Player Answer Selection Model`.

Backend chat mutation не знает о несохранённом draft.

---

# 11. Replace mutation

## 11.1 Intent

Replace используется, когда ведущий сообщает:

> Этот fragment является новой полной версией чата вопроса.

Типовые сценарии:

- вставлен чат не от того вопроса;
- прошлый импорт оказался неполным;
- требуется полностью перестроить effective set;
- ведущий скопировал правильный полный диапазон.

## 11.2 Pipeline

```text
rawText
→ parse
→ candidate filter
→ canonical identity
→ deduplicate inside new set
→ match old messages by canonicalKey
→ create new effective set
→ validate persisted answer references
→ rebuild read model
```

## 11.3 Invariant

> Replace полностью определяет новый effective chat state.

После replace отсутствующие old messages:

- удаляются из effective chat;
- исчезают из player groups;
- перестают быть available radio options;
- не участвуют в ranking.

## 11.4 Stable IDs

Если новое message совпадает со старым по canonical identity:

```text
old.canonicalKey == new.canonicalKey
```

backend сохраняет его:

```ts
id;
```

Новые logical messages получают новые IDs.

Removed messages исчезают из effective state.

## 11.5 Effective order

Retained message может сохранить `id`, но получает новый:

```ts
effectiveOrder;
```

соответствующий позиции в новом fragment.

## 11.6 Replace with no candidates

Если:

- rawText непустой;
- parser/filter не вернули candidates,

replace не применяется.

Backend возвращает ошибку или rejected result:

```text
Не найдено сообщений для замены.
Текущий чат не изменён.
```

Пустой effective chat создаётся только явной `clear` командой.

## 11.7 No-op replace

Если canonical set и effective order совпадают с текущими:

```ts
effectiveChange = false;
```

Тогда:

- reviewed сохраняется;
- persisted selections сохраняются;
- ranking не меняется;
- fragment attempt может сохраниться.

# 12. Persisted selections invalidated by replace

## 12.1 Problem

Persisted answer selections могут ссылаться на messages, удалённые новым replace.

```ts
interface QuizSelectedAnswer {
  playerName: string;
  selectedMessageId: string;
}
```

После физического удаления message dangling reference недопустима.

## 12.2 Decision

Replace атомарно удаляет из persisted selection set все записи, чей:

```ts
selectedMessageId;
```

больше не существует в новом effective chat.

Оставшиеся selections сохраняются, если:

- selected message retained;
- message всё ещё принадлежит тому же player group.

## 12.3 Consequences

Если persisted selection удалена:

- authoritative ranking пересчитывается без неё;
- reviewed сбрасывается;
- frontend local draft после response может создать новый unchecked group с первым radio;
- ведущий вручную решает, нужно ли включить игрока снова;
- backend не выбирает fallback автоматически.

## 12.4 Why not reject replace

Replace не блокируется из-за старых selections, потому что его назначение — исправить effective chat.

Требование сначала вручную очищать selections создало бы лишнюю ceremony.

## 12.5 Why not select fallback automatically

Backend не должен угадывать, какое новое message является правильным.

Правильный fallback является решением ведущего в local selection form.

## 12.6 Review

Любое удаление или изменение persisted selection вследствие replace считается effective result change и сбрасывает reviewed.

---

# 13. Clear mutation

## 13.1 Intent

Clear полностью удаляет effective chat вопроса.

Это отдельная команда:

```text
clearChat
```

Пустой replace не используется.

## 13.2 Effects

Clear атомарно:

- удаляет все effective messages;
- очищает persisted answer selections;
- очищает authoritative ranking;
- сбрасывает reviewed;
- сохраняет conductedOrder;
- не выполняет navigation.

## 13.3 Confirmation

Clear является destructive secondary action и требует подтверждения.

---

# 14. Player grouping read model

## 14.1 Identity

Player group определяется нормализованным nickname:

```ts
playerName;
```

Messages одного nickname объединяются независимо от transport.

Transport остаётся property конкретного message.

## 14.2 Read model

```ts
interface QuizPlayerMessageGroupView {
  playerName: string;
  messages: QuizChatMessageView[];
  persistedSelectedMessageId: string | null;
}
```

`persistedSelectedMessageId` означает только уже сохранённый backend result.

Он не содержит текущий несохранённый checkbox/radio draft.

## 14.3 Message view

```ts
interface QuizChatMessageView {
  id: string;
  text: string;
  timestamp: string | null;
  transport: ChatTransport;
  effectiveOrder: number;
}
```

Messages возвращаются в backend-defined order.

Frontend не сортирует их повторно другим алгоритмом.

---

# 15. Reviewed behavior

## 15.1 Append

Если append добавил хотя бы одно effective message:

```ts
reviewedAt = null;
reviewedByUserId = null;
```

Причина: ведущий должен проверить новый материал.

Даже если persisted selected set не изменился, новый chat content требует review.

No-op append не сбрасывает reviewed.

## 15.2 Replace

Replace сбрасывает reviewed, если изменились:

- canonical message set;
- effective order;
- player groups;
- persisted selections;
- authoritative ranking.

No-op replace не сбрасывает reviewed.

## 15.3 Clear

Clear всегда сбрасывает reviewed.

## 15.4 Conducted order

Chat mutations не изменяют:

```ts
conductedOrder;
```

Уже проведённый вопрос остаётся в той же фактической позиции.

## 15.5 Navigation

Chat mutation не открывает другой вопрос.

---

# 16. UI interaction model

## 16.1 Effective chat visibility

Ведущий всегда должен видеть текущий effective chat, который backend реально использует.

Пример:

```text
21:05 · private · Emrys: Минск
21:05 · clan · Darkness: Варшава
21:05 · to · Emrys: Москва
```

При одинаковом timestamp используется `effectiveOrder`.

## 16.2 Separate input

Effective preview и mutation textarea являются разными элементами:

```text
Собранный чат
[read-only effective preview]

Добавить фрагмент
[textarea]

[Добавить] [Заменить текущим содержимым]
```

## 16.3 After successful mutation

После append или replace textarea может очищаться, потому что применённый результат остаётся видимым в effective preview.

Frontend может временно сохранять последний raw input локально, но backend domain state от этого не зависит.

## 16.4 No lost context

Главный UX-инвариант:

> После импорта ведущий всегда видит, какой набор сообщений backend фактически собрал.

Он не должен зависеть от содержимого очищенного textarea.

## 16.5 Fragment history UI

Полная fragment history не является частью primary workflow.

При необходимости она доступна как:

- collapsible diagnostic details;
- admin/debug view;
- future support tooling.

---

# 17. Replace confirmation

Replace не требует modal confirmation.

Если effective chat непустой, используется inline confirmation:

```text
[Заменить текущий чат]
```

после первого клика:

```text
Текущий собранный чат будет заменён.

[Подтвердить замену] [Отмена]
```

Если effective chat пуст, replace эквивалентен первичной загрузке и дополнительное подтверждение может не требоваться.

---

# 18. Undo

Undo replace не входит в первую версию.

Полный undo потребовал бы сохранения:

- previous messages;
- previous effective order;
- previous persisted selections;
- previous reviewed state;
- previous ranking;
- potentially previous awards.

Raw fragments недостаточны для безопасного восстановления всей domain state.

До появления revision history replace защищается inline confirmation.

---


```json
{
  "rawText": "..."
}
```

## Clear

```http
DELETE /projects/:projectId/quiz-events/:eventId/questions/:questionId/chat
```

Application layer должен иметь отдельные use cases:

```text
appendChat
replaceChat
clearChat
```

Даже если routing implementation использует другой URL format, бизнес-семантика команд не объединяется в неясный generic method.

# 20. Mutation result

Append и replace возвращают updated event или question read model и structured result.

```ts
interface QuizChatMutationResult {
  event: QuizEventView;

  mutation: {
    fragmentId: string;
    mode: "append" | "replace";

    parsedMessagesCount: number;
    candidateMessagesCount: number;
    duplicateMessagesCount: number;

    previousMessagesCount: number;
    nextMessagesCount: number;

    addedMessagesCount: number;
    removedMessagesCount: number;
    retainedMessagesCount: number;

    removedPersistedSelectionsCount: number;

    effectiveChange: boolean;
  };
}
```

Точная структура может быть компактнее, но backend должен позволять UI показать понятный feedback.

Пример:

```text
Добавлено 42 сообщения
Игроков: 16
Дубликатов: 8
Сохранённый выбор удалён у 1 игрока
```

---

# 21. Atomicity

Любая mutation атомарна.

Если происходит:

- parser failure;
- validation failure;
- replace with zero candidates;
- repository failure;
- concurrency conflict;
- selection reference validation failure;
- unexpected domain failure,

не изменяются:

- effective chat;
- fragment history;
- persisted selections;
- reviewed;
- authoritative ranking;
- awards-related persisted state.

Mutation применяется полностью либо не применяется.

---

# 22. Concurrency

Chat mutation использует optimistic concurrency.

Устаревший frontend state не должен молча перезаписывать более свежий effective chat.

Request должен содержать или передавать текущую revision.

При conflict:

- mutation не применяется;
- UI загружает актуальную question/event version;
- local selection draft может быть повторно merged по правилам ADR-3.

---

# 23. Size limits

Специальное продуктовое ограничение на:

- количество строк;
- количество сообщений;
- число player groups

в первой версии не вводится.

Система должна поддерживать несколько сотен messages одного вопроса.

Общие infrastructure limits HTTP payload остаются implementation detail и используются только для защиты процесса от случайно чрезмерного body.

Отдельная abuse protection не требуется, поскольку доступ получают доверенные ведущие.

# 24. Retention and compaction

## 24.1 Open event

Пока event находится в статусе:

```text
open
```

backend сохраняет:

- raw fragments;
- all effective messages;
- provenance;
- effective order;
- persisted selected answers;
- mutation statistics.

Это необходимо для:

- append;
- replace;
- выбора alternative messages;
- возврата к старым вопросам;
- полноценного reopen до compaction;
- диагностики импорта.

## 24.2 Complete event

Завершение event не удаляет raw или effective chat немедленно.

Full state сохраняется в течение retention period.

## 24.3 Deferred compaction

После retention period completed event может быть compacted.

Конкретный срок и scheduler являются implementation details.

До реализации безопасного cleanup допускается хранить полный chat state без автоматического compaction.

## 24.4 Final answer snapshots

Перед удалением non-final messages backend материализует selected answer snapshots:

```ts
interface QuizFinalAnswerSnapshot {
  playerName: string;

  messageId: string;
  text: string;
  timestamp: string | null;
  transport: ChatTransport;
  effectiveOrder: number;

  selectedAt: string;
  selectedByUserId: string | null;
}
```

Нельзя оставлять только `selectedMessageId`, если source message будет удалено.

## 24.5 Compactable data

После retention могут удаляться:

- raw fragment text;
- alternative unselected messages;
- parser diagnostics;
- temporary provenance.

Сохраняются:

- final selected answer snapshots;
- final ranking;
- awards;
- summary;
- conductedOrder;
- review metadata;
- audit data наград.

## 24.6 Reopen after compaction

Backend должен различать:

```text
completed with full chat
compacted completed
```

После compaction нельзя создавать впечатление, что alternative messages доступны.

Полная reopen semantics compacted event определяется отдельной archival policy.

# 26. Invariants

## Effective chat invariants

1. `chatMessages` являются единственным active source of truth.
2. Каждый message имеет уникальный ID.
3. Каждый message имеет canonical identity.
4. Effective chat не содержит duplicate canonical keys.
5. `effectiveOrder` уникален в рамках question.
6. Fragment history не управляет active state.
7. Removed messages не хранятся как inactive records.

## Append invariants

1. Append не удаляет existing messages.
2. Append не изменяет existing IDs.
3. Append не изменяет existing effectiveOrder.
4. Append добавляет только canonical-unique messages.
5. Append дедуплицирует внутри fragment и против effective chat.
6. No-op append не сбрасывает reviewed.
7. Append не требует промежуточного Save selection form.

## Replace invariants

1. Replace полностью определяет новый effective set.
2. Canonical matches сохраняют ID.
3. Replace пересоздаёт effectiveOrder.
4. Missing old messages удаляются.
5. Replace с zero candidates не применяется.
6. No-op replace не сбрасывает reviewed.
7. Dangling persisted selections удаляются атомарно.
8. Backend не выбирает fallback answer автоматически.

## Clear invariants

1. Clear удаляет все effective messages.
2. Clear удаляет persisted answer selections.
3. Clear очищает ranking.
4. Clear сбрасывает reviewed.
5. Clear не меняет conductedOrder.

## Workflow invariants

1. Effective mutation сбрасывает reviewed.
2. No-op mutation не сбрасывает reviewed.
3. Chat mutation не выполняет navigation.
4. Completed event не редактируется без reopen.
5. Frontend local selection draft не является backend state.
6. Chat mutation не сохраняет checkbox/radio decisions.

# 27. Rejected alternatives

## 27.1 Replay fragments on every read

Отклонено, потому что:

- создаёт unnecessary event sourcing;
- усложняет replace;
- требует fragment lifecycle;
- повышает стоимость чтения;
- усложняет migrations.

## 27.2 Use sourceLineNumber as identity

Отклонено.

`sourceLineNumber` определяет position внутри fragment, но не logical identity.

## 27.3 Sort only by timestamp

Отклонено, потому что timestamp имеет точность только до минуты.

## 27.4 Always create new IDs after replace

Отклонено, потому что создаёт unstable references и unnecessary diffs.

## 27.5 Preserve old effectiveOrder after replace

Отклонено.

Replace объявляет новый complete order.

## 27.6 Persist automatic selections during append

Отклонено.

Chat mutation не должна принимать решение о правильности ответа.

## 27.7 Persist exclusion state

Отклонено.

Выключенный checkbox является частью frontend draft. Persisted set содержит только included answers.

## 27.8 Store `selectionOrigin`

Отклонено.

Automatic/manual distinction не нужен в backend domain model после batch Save.

## 27.9 Autosave selections after chat mutation

Отклонено.

Frontend должен позволять ведущему продолжить локальное редактирование и сохранить complete set позже.

## 27.10 Reject replace if old selections become invalid

Отклонено как лишняя ceremony.

Replace должен иметь возможность исправить chat state.

Invalid persisted selections удаляются атомарно.

## 27.11 Automatically choose fallback for removed selections

Отклонено.

Backend не знает, какое новое message является правильным.

## 27.12 Immediate compaction on complete

Отклонено, потому что ломает полноценный reopen и уничтожает alternatives слишком рано.

## 27.13 Modal confirmation for every replace

Отклонено.

Используется inline confirmation.

---

# 28. Consequences

## Positive

- chat domain отделён от selection form;
- append остаётся non-destructive;
- replace полностью перестраивает effective set;
- backend не угадывает правильные ответы;
- промежуточный Save перед append не нужен;
- stable IDs сохраняются;
- порядок сообщений внутри минуты сохраняется;
- dangling selections невозможны;
- frontend всегда видит actual effective chat;
- no-op mutations не создают лишний review cycle;
- недавно завершённый event можно полноценно reopen.

## Negative

- frontend должен merge-ить local draft после mutation;
- replace может удалить persisted selections;
- ведущему потребуется повторно отметить ответ после destructive replace;
- появляется `effectiveOrder`;
- required selection reference pruning усложняет replace;
- retention/compaction потребует отдельного cleanup;
- Mongo document может расти во время проведения;
- reopen after compaction потребует отдельной semantics.

## Accepted trade-off

Chat mutation не должна скрыто редактировать итог викторины.

Она меняет только доступный набор сообщений.

Выбор правильных ответов остаётся отдельным явным batch-действием ведущего.

---

# 29. Migration outline

Текущие messages содержат:

```ts
firstSeenFragmentId;
firstSeenOrder;
sourceLineNumber;
canonicalKey;
```

Предварительная migration:

```text
firstSeenOrder → effectiveOrder
firstSeenFragmentId → sourceFragmentId
```

Текущие `playerAnswers` необходимо преобразовать в:

```ts
selectedAnswers: QuizSelectedAnswer[];
```

Правила:

```text
accepted
→ сохранить playerName + selectedMessageId

rejected
→ не переносить

pending
→ не переносить
```

После migration:

1. проверить, что selected message существует;
2. проверить принадлежность message игроку;
3. удалить dangling references;
4. проверить uniqueness canonical keys;
5. пересобрать read model;
6. пересчитать ranking;
7. покрыть migration тестами.

---

# 30. Out of scope

Данный ADR не определяет:

- checkbox/radio local form behavior;
- Save selection set API;
- dirty-state navigation protection;
- semantic correctness ответа;
- ranking anchor через полночь;
- reward resolution;
- reward stability;
- retention duration;
- cleanup scheduler implementation;
- archival storage;
- individual message deletion;
- manual message editing;
- manual player creation;
- realtime collaborative editing.

Эти вопросы принадлежат другим ADR.

---

# 31. Final principle

> Chat mutation определяет, какие сообщения доступны ведущему. Она не определяет, какие ответы являются правильными.

Append расширяет effective chat.

Replace задаёт новую полную версию effective chat.

Clear удаляет effective chat.

Frontend после mutation обновляет локальную форму.

Persisted selection set меняется только после отдельного batch Save.
