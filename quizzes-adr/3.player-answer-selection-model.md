# ADR — Quiz Player Answer Selection Model

## Status

**Proposed**

## Related decisions

- `ADR — Quiz Chat Processing`
- `ADR — Quiz Host Workflow`
- `ADR — Quiz Chat Mutation Model`
- `ADR — Quiz Reward Stability` — planned

---

# 1. Context

После импорта чата backend возвращает текущий effective chat вопроса, сгруппированный по игрокам.

Один игрок может отправить несколько сообщений:

```text
Emrys

21:05 · private · Варшава
21:05 · clan   · Минск
21:06 · to     · Минск?
```

Backend не определяет семантическую правильность сообщений.

Ведущий должен:

1. определить, ответил ли игрок правильно хотя бы в одном сообщении;
2. включить или не включить игрока в результат;
3. если игрок включён — выбрать ровно одно его сообщение;
4. после проверки всех групп сохранить полный набор правильных ответов;
5. получить пересчитанный ranking.

Текущая модель использует для каждого игрока persisted status:

```text
pending
accepted
rejected
```

и отдельный `selectedMessageId`.

Также текущий UI сохраняет решение игрока отдельной backend-командой.

Такая модель не соответствует требуемому workflow.

Ведущий не должен отправлять отдельную mutation после каждого checkbox или radio click. Проверка ответов является одной локальной формой, которая сохраняется целиком после завершения редактирования.

---

# 2. Problem statement

Необходимо определить модель, при которой:

- backend возвращает все сообщения, сгруппированные по игрокам;
- frontend позволяет локально подготовить итоговый набор правильных ответов;
- checkbox определяет участие игрока;
- radio определяет конкретное учитываемое сообщение;
- пользовательские клики не вызывают backend mutations;
- несколько изменений сохраняются одной командой;
- backend принимает authoritative snapshot выбранных ответов;
- ranking обновляется только после сохранения;
- append нового фрагмента не требует промежуточного сохранения формы;
- несохранённый frontend draft может быть перестроен с учётом нового effective chat.

---

# 3. Decision drivers

## 3.1 Защита от случайных кликов

Checkbox и radio являются частыми операторскими действиями.

Случайный клик не должен немедленно:

- менять persisted result;
- пересчитывать награды;
- сбрасывать review;
- отправлять backend request.

## 3.2 Batch workflow

Проверка ответов одного вопроса является единой операцией ведущего.

Backend должен получать полный итоговый set, а не последовательность мелких команд.

## 3.3 Минимум backend ceremony

Backend не должен моделировать отдельные команды:

```text
accept player
reject player
restore player
select message
```

Он должен принимать готовый authoritative selection set.

## 3.4 Явное сохранение

До нажатия Save все checkbox/radio changes считаются frontend draft.

После Save backend становится источником истины для сохранённого selection set.

## 3.5 Простая persisted-модель

Persisted state содержит только ответы, которые участвуют в результате.

Игрок, отсутствующий в persisted set, не учитывается.

Не нужны persisted records для:

- неправильных игроков;
- временно выключенных checkbox;
- automatic/manual UI choices;
- промежуточной формы.

---

# 4. Decision

Проверка ответов реализуется как локальная frontend-форма над backend-provided player groups.

Frontend позволяет ведущему:

- включить игрока checkbox;
- выключить игрока checkbox;
- выбрать одно сообщение radio;
- включить всех через `Select All`;
- изменить любое количество решений;
- сохранить полный selection set одной backend-командой.

До сохранения backend state не меняется.

---

# 5. Player grouping

## 5.1 Group identity

Player group определяется нормализованным nickname:

```ts
interface QuizPlayerMessageGroupView {
  playerName: string;
  messages: QuizChatMessageView[];
}
```

Сообщения одного nickname объединяются независимо от transport.

Transport остаётся характеристикой конкретного сообщения.

## 5.2 Messages

Группа содержит все effective messages игрока, прошедшие:

```text
Parser
→ Candidate Filter
→ Deduplicator
→ Effective Chat Persistence
```

Frontend не выполняет дополнительную дедупликацию.

## 5.3 Message ordering

Сообщения внутри группы уже возвращаются backend в правильном порядке:

```text
relative timestamp
→ effectiveOrder
```

Frontend не должен применять альтернативную сортировку.

---

# 6. Local selection draft

## 6.1 Model

Frontend хранит локальный draft для каждой player group:

```ts
interface QuizPlayerAnswerDraft {
  playerName: string;

  isSelected: boolean;
  selectedMessageId: string;
}
```

`selectedMessageId` существует даже при:

```ts
isSelected === false;
```

Это позволяет:

- заранее иметь валидный radio default;
- не терять radio при случайном выключении checkbox;
- повторно включить игрока без дополнительного выбора.

## 6.2 Draft is not domain state

Local draft:

- не является частью `QuizEvent`;
- не сохраняется после каждого изменения;
- не влияет на ranking до Save;
- не влияет на awards до Save;
- не сбрасывает reviewed до Save;
- не вызывает backend requests при checkbox/radio changes.

## 6.3 Dirty state

Форма считается dirty, если локальный authoritative set отличается от persisted selections, полученных от backend.

Frontend должен явно показывать возможность сохранения.

Кнопка Save disabled, когда effective set не изменился.

---

# 7. Initial form construction

## 7.1 Persisted selected player

Если backend уже содержит persisted selection для игрока:

```ts
{
  playerName: "Emrys",
  selectedMessageId: "message-2"
}
```

frontend создаёт:

```ts
{
  playerName: "Emrys",
  isSelected: true,
  selectedMessageId: "message-2"
}
```

при условии, что message остаётся effective и принадлежит игроку.

## 7.2 Player without persisted selection

Если игрок присутствует в effective chat, но отсутствует в persisted selection set:

```ts
{
  playerName: "Darkness",
  isSelected: false,
  selectedMessageId: earliestMessageId
}
```

Новый игрок по умолчанию не считается ответившим правильно.

Ведущий явно включает его checkbox либо использует `Select All`.

## 7.3 Default radio

Для каждой группы всегда выбран один radio.

Default message:

```text
earliest message by backend ordering
```

То есть:

```text
relative timestamp
→ effectiveOrder
```

Radio выбирается заранее даже при выключенном checkbox.

Это позволяет включить игрока одним кликом без дополнительного обязательного выбора.

## 7.4 Semantic meaning

Предварительно выбранный radio не означает, что сообщение признано правильным.

Он является только удобным UI default.

Игрок участвует в будущем selection set только при:

```ts
isSelected === true;
```

---

# 8. Checkbox behavior

## 8.1 Player checkbox

Checkbox означает:

```text
checked
→ игрок будет включён в selection set при Save
```

```text
unchecked
→ игрок отсутствует в selection set
```

Выключение checkbox:

- не удаляет сообщения;
- не очищает выбранный radio;
- не вызывает backend request;
- не изменяет persisted result до Save.

## 8.2 Enabling player

При включении checkbox используется текущий локальный:

```ts
selectedMessageId;
```

Поскольку первый radio выбран заранее, группа всегда готова к включению.

## 8.3 Disabling player

При выключении checkbox выбранный radio сохраняется в local draft.

Если checkbox включить повторно до Save, предыдущий локальный выбор восстанавливается автоматически.

Отдельных понятий:

```text
exclude
restore
return player
```

в доменной или API-модели нет.

Это только изменение boolean-поля локальной формы.

---

# 9. Radio behavior

## 9.1 Selection

Один игрок может иметь ровно один выбранный radio в local draft.

Клик по radio:

- меняет только локальный `selectedMessageId`;
- не включает игрока автоматически;
- не отправляет backend request;
- не меняет persisted ranking.

Checkbox и radio являются независимыми контролами:

```text
checkbox
→ участвует ли игрок
```

```text
radio
→ какое сообщение будет использовано, если игрок участвует
```

## 9.2 Repeated click

Повторный клик по уже выбранному radio ничего не меняет.

Radio не используется как checkbox и не выключает игрока.

## 9.3 Disabled visual state

При выключенном checkbox radio может оставаться выбранным и доступным для изменения.

Моя рекомендуемая UX-модель:

- сообщения остаются видимыми;
- выбранный radio остаётся видимым;
- ведущий может сначала выбрать правильное сообщение, затем включить checkbox;
- группа визуально приглушена, пока checkbox выключен.

Radio не обязан быть disabled.

Это позволяет проверять сообщения в любом удобном порядке.

---

# 10. Select All

## 10.1 Intent

Форма содержит общий checkbox:

```text
Select All
```

или локализованную подпись:

```text
Учитывать всех
```

## 10.2 Behavior

Если не все игроки выбраны:

```text
Select All
→ isSelected = true для всех групп
```

Если все игроки выбраны:

```text
Select All
→ isSelected = false для всех групп
```

Операция:

- локальная;
- не вызывает backend request;
- не изменяет radio selections;
- не сохраняет результат автоматически.

## 10.3 Primary usage

Поддерживаются оба рабочих сценария.

### Мало правильных ответов

Ведущий включает только нужных игроков.

### Большинство ответило правильно

Ведущий:

```text
Select All
→ снимает checkbox у неправильных
→ Save
```

Это позволяет избежать большого количества однотипных кликов.

---

# 11. Visual grouping

## 11.1 Included players

Игроки с включённым checkbox визуально относятся к группе:

```text
Ответили верно
```

или:

```text
Учитываются
```

## 11.2 Unselected players

Игроки с выключенным checkbox отображаются ниже под заголовком:

```text
Ответили неверно
```

Их сообщения остаются доступными для просмотра и изменения radio.

## 11.3 Reordering while editing

Немедленное физическое перемещение карточки после каждого checkbox click может мешать ведущему и приводить к потере визуального контекста.

Рекомендуемое поведение:

- во время активного редактирования карточки сохраняют стабильный порядок;
- selected/unselected state отображается визуально;
- после Save или полной перестройки формы группы могут быть разделены на:
  - `Ответили верно`;
  - `Ответили неверно`.

Допустима реализация с двумя секциями, если перемещение карточек не приводит к UX-проблемам.

Ключевой инвариант:

> Выключенные игроки располагаются ниже или явно отделяются от включённых, но не исчезают из формы.

## 11.4 Stable group ordering

Внутри соответствующей секции player groups сортируются по earliest effective message:

```text
earliest relative timestamp
→ earliest effectiveOrder
```

Карточки не сортируются по текущему ranking, чтобы не прыгать при смене radio.

---

# 12. Message presentation

Каждая message row содержит:

```text
radio
timestamp
transport
text
```

Пример:

```text
○ 21:05 · to      Варшава
● 21:05 · private Минск
○ 21:06 · clan    Минск?
```

Transport отображается в исходной семантике:

```text
to
private
clan
```

`effectiveOrder` используется для сортировки, но не показывается ведущему.

Сообщение без timestamp отображается как:

```text
без времени
```

и сортируется backend согласно общей ranking policy.

---

# 13. Updating draft after chat append

## 13.1 No intermediate save

Ведущий может:

1. изменить checkbox/radio;
2. не сохранять форму;
3. добавить новый chat fragment;
4. продолжить проверку уже обновлённой формы.

Промежуточный Save перед append не требуется.

## 13.2 Merge behavior

После append backend возвращает обновлённые effective player groups.

Frontend перестраивает local draft, сохраняя совместимые локальные решения.

Для каждой существующей группы:

- `isSelected` сохраняется;
- выбранный message сохраняется, если он остаётся effective;
- если выбранное message исчезло, выбирается новый earliest default;
- новые messages добавляются в группу;
- новые player groups создаются с:
  - `isSelected = false`;
  - earliest radio selected.

Append по определению не удаляет existing messages, поэтому исчезновение выбранного сообщения при append в нормальном сценарии не ожидается.

## 13.3 Unsaved local state

Backend ничего не знает о local draft и не пытается его reconciliation.

Merge выполняется frontend на основании:

- предыдущего local draft;
- нового backend read model.

## 13.4 Dirty state after append

Если до append форма была dirty, она остаётся dirty.

Если append добавил новых игроков или messages, форма также может стать dirty относительно persisted selection set.

---

# 14. Updating draft after chat replace

Replace может удалить ранее доступные messages и player groups.

Frontend перестраивает draft по следующим правилам.

## 14.1 Existing player and existing selected message

Сохраняются:

```text
isSelected
selectedMessageId
```

## 14.2 Existing player but selected message disappeared

Frontend:

- сохраняет текущее `isSelected`;
- выбирает earliest available message как новый local radio default;
- помечает форму dirty;
- может показать ненавязчивое уведомление, что часть выбора была обновлена.

## 14.3 Player disappeared

Player group удаляется из local draft.

Если игрок присутствовал в persisted set, новый local authoritative set больше его не содержит и форма становится dirty.

## 14.4 New player

Создаётся:

```ts
{
  isSelected: false,
  selectedMessageId: earliestMessageId
}
```

## 14.5 No automatic backend save

Ни одно из этих изменений не сохраняется автоматически.

Ведущий проверяет обновлённую форму и явно нажимает Save.

---

# 15. Save operation

## 15.1 Intent

Save отправляет полный authoritative selection set текущего вопроса.

Кнопка может называться:

```text
Сохранить результаты
```

## 15.2 Request model

```ts
interface QuizSelectedAnswerInput {
  playerName: string;
  selectedMessageId: string;
}

interface SaveQuizAnswerSelectionsRequest {
  selections: QuizSelectedAnswerInput[];
}
```

В request включаются только группы, где:

```ts
isSelected === true;
```

Игрок с выключенным checkbox отсутствует в массиве.

## 15.3 Full replacement semantics

Backend рассматривает request как полную новую версию selection set вопроса:

```ts
question.selectedAnswers = validatedRequestSelections;
```

Это не patch.

Backend не вычисляет отдельные команды:

- добавить игрока;
- исключить игрока;
- вернуть игрока;
- изменить одно сообщение.

Он сравнивает предыдущий и новый complete set.

## 15.4 Atomicity

Save является атомарной операцией.

Либо весь selection set:

- валидируется;
- сохраняется;
- участвует в ranking;

либо persisted state не меняется.

Частичное сохранение отдельных игроков запрещено.

---

# 16. Persisted model

Persisted-модель содержит только включённые ответы:

```ts
interface QuizSelectedAnswer {
  playerName: string;
  selectedMessageId: string;
}
```

Допустимы audit metadata на уровне сохранения:

```ts
interface QuizAnswerSelectionState {
  selections: QuizSelectedAnswer[];

  updatedAt: string | null;
  updatedByUserId: string | null;
}
```

Отдельная запись для выключенного игрока не хранится.

Отсутствие игрока означает:

```text
player does not participate in ranking
```

Persisted statuses:

```text
pending
accepted
rejected
```

удаляются.

Persisted `selectionOrigin` также отсутствует.

---

# 17. Backend validation

При Save backend проверяет:

1. event существует;
2. event находится в `open`;
3. actor имеет право редактирования;
4. question принадлежит event;
5. отсутствуют duplicate `playerName`;
6. отсутствуют duplicate `selectedMessageId`;
7. каждый selected message существует в effective chat;
8. каждый selected message принадлежит указанному player;
9. каждый player имеет не более одного selected message;
10. request построен относительно актуальной event revision.

При нарушении любого инварианта весь request отклоняется.

---

# 18. Idempotency

Если новый canonical selection set совпадает с persisted set:

```text
Save
→ no-op success
```

В таком случае:

- selections не изменяются;
- reviewed не сбрасывается;
- ranking не изменяется;
- awards не должны пересчитываться;
- `updatedAt` может не меняться;
- frontend получает актуальный read model;
- dirty state очищается.

Порядок элементов входного массива не должен сам по себе считаться изменением.

Для сравнения set нормализуется детерминированно.

---

# 19. Ranking update

После effective Save backend:

1. сохраняет selected answers;
2. строит ranking только по выбранным messages;
3. сортирует их согласно backend ranking policy;
4. пересчитывает зависимые projections;
5. возвращает обновлённый question/event read model.

Отдельных кнопок:

```text
Пересчитать
Применить
Подтвердить каждого
```

нет.

До Save preview ranking может:

- оставаться последним persisted ranking;
- либо дополнительно вычисляться frontend как локальный preview.

## Decision for v1

Backend ranking является authoritative.

Frontend не обязан вычислять точный local preview до Save.

После Save ranking обновляется немедленно из backend response.

---

# 20. Reviewed behavior

Checkbox и radio clicks не сбрасывают reviewed, потому что являются несохранённым local draft.

Если Save реально изменил persisted selection set:

```ts
reviewedAt = null;
reviewedByUserId = null;
```

Если Save является no-op:

- reviewed сохраняется.

Save:

- не меняет `conductedOrder`;
- не выполняет навигацию;
- не отмечает вопрос reviewed автоматически.

Review и переход к следующему вопросу выполняются отдельным workflow action после проверки сохранённого результата.

---

# 21. Unsaved changes

## 21.1 Navigation

При попытке покинуть вопрос с dirty selection draft frontend должен защищать пользователя от случайной потери формы.

Допустимые реализации:

- inline warning;
- browser-style confirmation;
- сохранение draft в local storage.

## Recommendation for v1

При навигации к другому вопросу показывается компактное подтверждение:

```text
Есть несохранённые изменения ответов.
Перейти без сохранения?
```

Доступные действия:

```text
Сохранить и перейти
Перейти без сохранения
Остаться
```

Это один из немногих допустимых confirmation flows, потому что иначе пользовательские решения будут потеряны.

## 21.2 Page refresh

Для первой версии допускается browser beforeunload protection.

Persisted local draft recovery после полного refresh не является обязательным, но может быть добавлено через local storage.

## 21.3 Chat append

Append не считается уходом со страницы и не требует Save.

Local draft merge выполняется автоматически.

---

# 22. Select All and validation

Поскольку каждая группа всегда имеет заранее выбранный radio:

```text
Select All
→ форма сразу остаётся валидной
```

Нет состояния:

```text
checkbox checked
selectedMessageId missing
```

Если player group содержит хотя бы одно message, она всегда имеет local radio default.

Группа без сообщений не должна существовать в read model.

---

# 23. UI layout

## 23.1 Toolbar

Над группами располагаются:

```text
[Select All]

Выбрано: 10 из 15

[Сохранить результаты]
```

Save:

- enabled только при dirty state;
- показывает loading только на время batch request;
- не блокирует предварительные checkbox/radio clicks до отправки.

## 23.2 Player group

Пример:

```text
┌─────────────────────────────────────────────┐
│ ☑ Emrys                                     │
│                                             │
│ ○ 21:04 · private  Варшава                  │
│ ● 21:05 · clan     Минск                    │
│ ○ 21:05 · to       Минск?                   │
└─────────────────────────────────────────────┘
```

Неправильный игрок:

```text
┌─────────────────────────────────────────────┐
│ ☐ Darkness                                  │
│                                             │
│ ● 21:05 · private  Повторите вопрос         │
└─────────────────────────────────────────────┘
```

Отдельные action buttons:

```text
Принять
Отклонить
Вернуть
В ожидание
```

отсутствуют.

## 23.3 Density

Интерфейс является desktop-first операторской формой.

Требования:

- компактные outlined groups;
- небольшие вертикальные отступы;
- отсутствие большого `CardContent` вокруг каждого игрока;
- radio rows легко сканируются;
- длинные сообщения переносятся;
- controls остаются достаточно крупными для уверенного клика;
- никаких status chips на каждой группе.

## 23.4 Mobile

На mobile:

- группы располагаются одной колонкой;
- controls не создают horizontal scroll;
- Save остаётся доступным;
- sticky ranking может отключаться.

Основной сценарий остаётся desktop-first.

# 24. Ranking presentation

Persisted ranking отображается отдельным компактным блоком:

```text
Результат вопроса

1. Emrys — 21:05
2. Joker — 21:05
3. Darkness — 21:06
```

Ranking не заменяет selection form.

Selection form отвечает на вопрос:

> Какие сообщения должны учитываться?

Ranking отвечает на вопрос:

> В каком порядке расположены сохранённые правильные ответы?

Карточки player groups не сортируются по ranking, чтобы не перемещаться при редактировании.

Допустимо показывать position badge после Save, но authoritative result остаётся отдельным блоком.

Awards могут отображаться только как backend-provided projection. Selection UI не рассчитывает награды самостоятельно.

# 25. API

Рекомендуемый endpoint:

```http
PUT /projects/:projectId/quiz-events/:eventId/questions/:questionId/answer-selections
```

Payload:

```json
{
  "selections": [
    {
      "playerName": "Emrys",
      "selectedMessageId": "message-2"
    },
    {
      "playerName": "Joker",
      "selectedMessageId": "message-8"
    }
  ],
  "revision": 17
}
```

Response:

```ts
interface SaveQuizAnswerSelectionsResult {
  event: QuizEventView;

  result: {
    previousSelectionsCount: number;
    nextSelectionsCount: number;
    effectiveChange: boolean;
  };
}
```

Endpoint заменяет полный selection set.

Endpoints по одному игроку не создаются.

---

# 26. Concurrency

Поскольку frontend редактирует локальный draft, effective chat может измениться до Save:

- в другой вкладке;
- другим editor;
- после concurrent replace;
- после устаревшего append response.

Backend обязан проверить revision.

При conflict:

- selections не сохраняются;
- frontend загружает актуальный question;
- local draft может быть повторно merged;
- ведущему показывается, что данные вопроса изменились.

Backend не должен частично принимать selection set, построенный на устаревших message IDs.

---

# 27. Compacted events

После archival compaction alternative messages могут быть удалены.

Compacted event хранит:

- final selected answer snapshots;
- final ranking;
- awards;
- summary.

Полноценная checkbox/radio selection form недоступна без alternative messages.

Completed event до compaction остаётся read-only, но после reopen может восстановить полную форму.

Reopen после compaction определяется отдельной archival policy.

---

# 28. Invariants

## Group invariants

1. Player group определяется нормализованным nickname.
2. Player group содержит минимум одно effective message.
3. Одно message принадлежит ровно одной player group.
4. Сообщения группы возвращаются в backend-defined order.

## Local draft invariants

1. Каждая группа имеет boolean `isSelected`.
2. Каждая группа имеет ровно один local selected radio.
3. Radio существует независимо от checkbox state.
4. Checkbox/radio changes не вызывают backend requests.
5. Несохранённый draft не влияет на authoritative ranking.
6. Новый player по умолчанию unchecked.
7. Первый radio нового player выбран заранее.
8. Select All меняет только checkbox state.

## Persisted selection invariants

1. Persisted set содержит только учитываемых игроков.
2. Один player встречается максимум один раз.
3. Один player имеет ровно одно selected message.
4. Selected message принадлежит этому player.
5. Отсутствующий player не участвует в ranking.
6. Persisted status для неправильного player отсутствует.
7. Save полностью заменяет persisted set.
8. Save атомарен.

## Workflow invariants

1. Effective Save пересчитывает ranking.
2. Effective Save сбрасывает reviewed.
3. No-op Save не сбрасывает reviewed.
4. Save не меняет conductedOrder.
5. Save не выполняет navigation.
6. Append может обновлять local draft без промежуточного Save.
7. Dirty draft защищён при уходе с вопроса.

# 29. Rejected alternatives

## 29.1 Autosave each checkbox or radio

Отклонено, потому что:

- случайные клики сразу меняют persisted result;
- создаётся большое количество backend requests;
- ranking и awards постоянно пересчитываются;
- ведущий не может спокойно подготовить форму;
- rollback ошибки становится сложнее.

## 29.2 Persist `pending/accepted/rejected`

Отклонено, потому что persisted result требует только выбранных правильных сообщений.

Отдельный status неправильного игрока не имеет самостоятельной бизнес-ценности.

## 29.3 Separate exclude/restore commands

Отклонено, потому что checkbox является локальным boolean формы.

Backend получает полный set и не должен интерпретировать пользовательское редактирование как последовательность команд.

## 29.4 Nullable persisted selection per player

Отклонено.

Игрок с выключенным checkbox просто отсутствует в authoritative selection set.

## 29.5 Persist automatic/manual origin

Отклонено, потому что default radio существует только в frontend draft.

Backend получает уже готовое явное решение после Save.

## 29.6 Save one player at a time

Отклонено, потому что проверка одного вопроса является batch operation.

## 29.7 Require intermediate Save before append

Отклонено, потому что ведущий может дозагружать чат во время проверки.

Frontend должен merge-ить local draft с обновлённым effective chat.

## 29.8 No explicit Save

Отклонено из-за риска случайных persisted changes.

## 29.9 Multiple selected messages per player

Отклонено, потому что один player не должен занимать несколько ranking positions в одном вопросе.

## 29.10 Remove or edit individual chat messages

Отклонено для первой версии.

Selection form выбирает сообщения, но не редактирует effective chat. Исправление набора чата выполняется через append/replace/clear.

# 30. Consequences

## Positive

- случайные клики не меняют backend state;
- ведущий проверяет весь вопрос как одну форму;
- используется один batch request;
- persisted model становится минимальной;
- неправильные игроки не требуют отдельных status records;
- Select All поддерживает сценарий с большинством правильных ответов;
- radio default уменьшает количество кликов;
- append не требует промежуточного Save;
- backend validation работает над полным authoritative set;
- ranking обновляется один раз после Save;
- frontend workflow становится понятным и предсказуемым.

## Negative

- frontend должен хранить local draft;
- требуется dirty-state detection;
- требуется merge draft после append/replace;
- несохранённые изменения нужно защищать при navigation;
- ranking до Save может показывать предыдущий persisted result;
- concurrent backend changes требуют reconciliation;
- часть selection logic находится на frontend по дизайну.

## Accepted trade-off

Frontend intentionally owns temporary form state, а backend owns saved result.

Это считается правильным разделением ответственности:

```text
frontend
→ пользователь готовит решение

backend
→ валидирует и сохраняет итоговое решение
```

Дополнительная frontend-сложность оправдана тем, что ведущий получает безопасный batch workflow без autosave и множества формальных действий.

# 31. Required correction to Chat Mutation ADR

Ранее предложенная модель backend-owned automatic selections должна быть удалена из `ADR — Quiz Chat Mutation Model`.

Chat mutations не должны persisted-автоматически:

- выбирать answers новых игроков;
- создавать exclusion records;
- изменять answer selections;
- хранить `selectionOrigin`;
- сохранять automatic/manual decisions.

Append и replace отвечают только за:

- effective chat;
- player groups;
- message identities;
- ordering;
- сохранение или удаление messages.

Reconciliation несохранённой selection form после chat mutation выполняется frontend согласно данному ADR.

Persisted selections изменяются только через batch Save endpoint.

При replace backend может удалить messages, на которые ссылается старый persisted selection set. В таком случае реализация должна выбрать одну из согласованных безопасных стратегий:

1. atomically удалить ставшие невалидными persisted selections и сбросить reviewed;
2. отклонить replace до явного обновления selection set;
3. сохранить denormalized snapshot, но исключить dangling selection из active ranking.

Точная backend-стратегия для invalidated persisted selections должна быть окончательно определена в revised Chat Mutation ADR и согласована с Reward Stability ADR.

---

# 32. Out of scope

Данный ADR не определяет:

- semantic correctness сообщения;
- точный ranking anchor;
- reward resolution;
- стабильность случайных наград;
- replacement policy для awards;
- UI styling beyond workflow requirements;
- local storage recovery implementation;
- individual message deletion;
- manual player creation;
- message text editing;
- collaborative realtime form editing.

---

# 33. Final principle

> Ведущий сначала готовит полный набор правильных ответов, затем сохраняет его одним действием.

Checkbox определяет, участвует ли игрок.

Radio определяет, какое сообщение игрока участвует.

До Save это только локальная форма.

После Save backend принимает полный authoritative set и пересчитывает результат.
