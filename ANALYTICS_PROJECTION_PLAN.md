# План модуля аналитики

## Предусловие

Этот модуль реализуется только после завершения эпопеи с игроками:

1. исторические игровые участники и Quiz Event selections получили `playerRefId`;
2. новые игры и новые участники получают `playerRefId` до вызова engine;
3. отчёт миграции не содержит нерешённых участников.

До этого аналитика не должна повторно сопоставлять ники. Она работает только с `playerRefId`.

## Назначение

Analytics не является вторым источником игровой истины. Канонические данные остаются в завершённых играх и Quiz Events.

Коллекция analytics хранит materialized projection — пересчитываемое представление, ускоряющее запросы по участию и выданным наградам без обхода всех игровых документов при каждом открытии аналитики.

При расхождении всегда доверять источнику, удалить или заменить analytics fact и пересобрать его.

## Grain хранения

Один analytics fact соответствует одной проведённой сущности:

- завершённой игре;
- завершённому Quiz Event.

Участники и их агрегированные результаты хранятся внутри этого факта. Это проще для первичной реализации, чем отдельные записи на игрока, и естественно соответствует жизненному циклу источника.

```ts
interface AnalyticsResult {
  id: string;
  projectId: string;
  occurredAt: string;

  source: {
    kind: "game" | "quiz_event";
    type: "journey" | "lotto" | "lotto_bingo" | "battleships" | "quiz";
    id: string;
    quizId?: string;
    revision: number | null;
    updatedAt: string;
  };

  participants: Array<{
    playerRefId: string;
    nicknameSnapshot: string;

    rewards: {
      regular: RewardGrant[];
      bonus: RewardGrant[];
    };

    // Добавляется только когда нужен общий для продукта показатель,
    // например место победителя или число успешных действий.
    metrics?: Record<string, number | string | boolean | null>;
  }>;

  resourceSnapshot: ResourceSnapshot[];

  meta: {
    status: "ready" | "partial";
    computedAt: string;
    schemaVersion: 1;
  };
}
```

`RewardGrant` должен содержать уже сохранённый результат выдачи, а не `RewardPool` с правилами будущего розыгрыша.

Каждая игра самостоятельно через свой адаптер определяет:

- кого считать участником;
- какие сохранённые выдачи отнести к `regular`;
- какие — к `bonus`;
- какие дополнительные итоговые metrics нужны для её аналитики.

Analytics не пытается вывести эти решения самостоятельно и не переигрывает RewardPool.

## Что позволит считать первая версия

- число участий игрока, уникальных участников и активность по периодам;
- суммы regular и bonus наград по игроку, ресурсу, проекту, типу игры и периоду;
- лидерборды заработка и частоты участия;
- распределение выданных наград по играм и Quiz Events;
- сравнение типов игр по участию и объёму наград.

Точность Battleships, количество ходов Journey, места Lotto или другие доменные показатели не появляются автоматически. Их добавляет соответствующий адаптер только при наличии чёткой продуктовой потребности.

## Индексы

Один факт на источник в проекте:

```ts
{ projectId: 1, "source.kind": 1, "source.id": 1 } // unique
```

Основной диапазонный индекс:

```ts
{ projectId: 1, occurredAt: -1, "source.type": 1 }
```

Для запросов по игрокам используется `$unwind` массива `participants`. Отдельную per-player projection добавлять только при реальной проблеме производительности.

## Построение facts

Для каждого игрового модуля и Quiz Event создать adapter/factory, который читает только финальное сохранённое состояние и строит `AnalyticsResult`.

```text
Finished source → Module analytics adapter → AnalyticsProjectionService → AnalyticsRepository
```

Создавать или заменять fact только после перехода источника в финальный статус `finished` / `completed`.

- Engines по-прежнему не знают о MongoDB и AnalyticsRepository.
- Сервис игры сохраняет источник как завершённый.
- Затем ставится асинхронная идемпотентная задача построения факта.
- Upsert выполняется по `projectId + source.kind + source.id` и заменяет fact целиком.

Не использовать простой fire-and-forget Promise как единственный механизм: перезапуск процесса может потерять задачу. MVP должен как минимум иметь повторяемый refresh/reconciliation; позднее допустим durable outbox или очередь.

## Удаление и переоткрытие источников

Analytics fact должен исчезать, если его источник перестал быть проведённым:

- при удалении завершённой игры или Quiz Event сервис удаляет fact по source key;
- при переоткрытии `finished`-источника fact удаляется или помечается неактуальным;
- при удалении проекта удаляются все analytics facts этого проекта.

Эти точечные операции ускоряют консистентность. Refresh остаётся обязательной страховкой от ошибок фоновой задачи, перезапусков и ручных изменений базы.

## Refresh и reconciliation

### Полный refresh проекта

`refreshProject(projectId)` логически пересобирает аналитику с нуля:

1. находит все завершённые games и Quiz Events проекта;
2. строит актуальные facts через адаптеры;
3. upsert-ит их в analytics;
4. только после успешного построения удаляет orphan facts, источники которых удалены или больше не завершены.

Не удалять все facts в начале refresh: при ошибке посередине текущая аналитика должна оставаться доступной.

Полный refresh всех проектов — отдельная административная/offline операция.

### Проверка свежести при открытии Analytics

При открытии аналитики текущего проекта выполнять integrity-проверку:

1. количество завершённых sources и facts по каждому `source.type`;
2. missing facts: завершённые источники без facts;
3. orphan facts: facts без источника или для незавершённого источника;
4. несовпадение `source.revision` / `source.updatedAt`;
5. facts со статусом `partial`, например из-за нерешённого `playerRefId`.

Сравнения только количества недостаточно: при одинаковом числе документов могут одновременно существовать один пропущенный source и один orphan fact.

Страница должна возвращать кэш вместе с состоянием свежести:

```ts
"fresh" | "stale" | "refreshing"
```

Если найдена проблема, backend запускает refresh проекта. UI может показать текущие данные со статусом `stale`/`refreshing` и перечитать их после завершения. Отдельная ручная команда «Обновить аналитику» может ожидать завершения refresh.

## Критерии готовности

- Analytics facts строятся только из завершённых источников с `playerRefId`.
- Каждый source adapter читает сохранённые результаты, а не пересчитывает игровую логику или RewardPool.
- Повторная обработка одного source не дублирует награды.
- Удаление или переоткрытие проведённого источника удаляет его fact.
- Refresh проекта восстанавливает точное соответствие analytics и сохранённых проведённых источников.
- Integrity-проверка сообщает missing, orphan, stale и partial facts.
