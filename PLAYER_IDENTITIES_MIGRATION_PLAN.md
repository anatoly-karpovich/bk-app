# План внедрения ссылок на игроков в сохранённые игры

## Цель

Связать участников игр с project-scoped коллекцией `players`, чтобы аналитика опиралась на стабильную сущность игрока, а не только на строковый ник.

`Player` не равен `User`:

- `User` — учётная запись ведущего или администратора приложения;
- `Player` — участник игр в одном конкретном проекте;
- один и тот же ник в разных проектах представляет разных `Player`.

## Текущее состояние

- Коллекция `players` существует и заполняется отдельной миграцией по сохранённым играм.
- Игрок хранит текущий `nickname`, его нормализованный ключ `nicknameKey` и все известные варианты имени в `aliases`:

  ```ts
  aliases: Array<{
    nickname: string;
    key: string;
  }>;
  ```

- Уникален только текущий ник: `{ projectId: 1, nicknameKey: 1 }`. Алиасы не уникальны и не используются для автоматического разрешения игрока: один ник мог принадлежать разным людям в разные периоды.
- `playerRefId` уже записывается во все новые Lotto Bingo, Lotto, Journey и Battleships игры. Их engines принимают только заранее разрешённую identity с обязательным `playerRefId`.
- На момент подключения Lotto, Journey и Battleships в единственном проекте не было сохранённых партий. Поэтому историческая миграция для этих трёх коллекций не требуется и не запускается.
- Чтение старых документов остаётся tolerant: поле в сохранённой сущности временно необязательно, чтобы не ломать импорт старых backup.
- В текущем single-operator rollout удаление Player разрешено, когда `PlayerReferencesRepository` не находит его `playerRefId` ни в одном сохранённом game/Event. Проверка не использует nickname fallback и не защищает от конкурентного добавления ссылки. Transactional lifecycle текущих ссылок остаётся отдельным будущим этапом.

## Целевая модель идентичности

Игровой участник сохраняет два разных идентификатора:

```ts
{
  id: string; // локальный идентификатор участника в конкретной партии
  playerRefId: string; // ссылка на players._id
  nickname: string; // неизменяемый снимок имени на момент игры
}
```

Локальный `id` нельзя заменять на `playerRefId`: на нём уже построены ходы, выплаты, победы и другие правила конкретной партии.

`nickname` также нельзя заменять чтением текущего `Player.nickname`: историческая партия должна отображать имя, с которым игрок участвовал в ней.

## Этап 1. Расширить игровые модели — выполнен для игр, кроме Quiz Events

Добавить временно необязательное поле `playerRefId` в сущности, которые являются источником идентичности участника:

| Модуль      | Место хранения ссылки                                                                   |
| ----------- | --------------------------------------------------------------------------------------- |
| Journey     | `stateV2.players[]`                                                                     |
| Lotto       | `players[]`                                                                             |
| Lotto Bingo | `players[]`                                                                             |
| Battleships | поле игры рядом с `playerName`, так как в партии один игрок                             |
| Quiz Events | `questions[].selectedAnswers[]`; награды и summary получают ссылку из выбранного ответа |

Не добавлять отдельные несогласованные ссылки в производные данные. Например, payout в Lotto уже ссылается на локальный id участника; этого достаточно, если сам участник содержит `playerRefId`.

Все публичные DTO менять только через соответствующие read-model factories. Не раскрывать `playerRefId` во frontend API, пока это не требуется продуктовой задачей.

Реализованные backend-совместимые входы, пока frontend не передаёт ссылку:

- Lotto принимает `playerRefId?: string | null` в существующем объекте игрока вместе с `nickname` и `cardNumbers`;
- Journey продолжает принимать `nicknames: string[]` и дополнительно принимает `players: Array<{ nickname, playerRefId? }>`;
- Battleships продолжает принимать `playerName` и дополнительно принимает `playerRefId?: string | null`;
- Lotto Bingo принимает `{ nickname, playerRefId?: string | null }` при добавлении игрока.

## Этап 2. Связать исторические игры

Создать отдельную офлайн-миграцию с `dry-run` по умолчанию и явным `--apply`.

Для каждого участника миграция:

1. Берёт `projectId` игры и ник-снимок участника.
2. Нормализует ник тем же правилом, что и `PlayersService`.
3. Ищет `Player` только в этом проекте по текущему `nicknameKey`; алиасы для автоматического сопоставления не используются.
4. Записывает найденный `playerRefId` в игровой документ.

Правила безопасности:

- Миграция не создаёт новых игроков: первая миграция уже собрала их из этих же сохранений.
- При отсутствии `Player` ссылка остаётся незаполненной, а запись попадает в отчёт `unresolved`.
- Сначала прогоняются local `dry-run` и `--apply`, затем production после свежего полного backup.
- После production выполняется повторный `dry-run`; он должен сообщить ноль нерешённых участников и ноль нуждающихся в изменении игр.

Статус:

- Lotto Bingo имеет отдельную офлайн-миграцию `db:migrate:lotto-bingo-player-refs`;
- для Journey, Lotto и Battleships миграции сейчас не нужны: сохранённых игр нет;
- если в будущем будет восстановлен backup с играми без `playerRefId`, до включения его в рабочую базу нужно добавить и выполнить соответствующую офлайн-миграцию по тем же правилам.

## Этап 3. Разрешать игроков в контроллерах конкретных игр — выполнен для Lotto Bingo, Lotto, Journey и Battleships

Добавить в `PlayersService` прикладной метод наподобие `resolveOrCreate`.

Контракты HTTP-запросов конкретных игр и Quiz Events временно принимают `playerRefId?: string | null`. Это относится к созданию Journey/Lotto/Battleships, добавлению игрока в Lotto Bingo и сохранению выбранных ответов Quiz Event.

Вход для создания игры или добавления участника:

```ts
{
  nickname: string;
  playerRefId?: string | null;
}
```

Поведение:

1. Если передан `playerRefId`, проверить, что `Player` существует и принадлежит проекту.
2. Если ссылка равна `null` или не передана, найти игрока только по нормализованному текущему `nicknameKey` в данном проекте.
3. Если игрок не найден, создать нового `Player` с указанным ником.
4. Вернуть сервису игры готовые `playerRefId` и `nickname`-снимок.

Если одновременно переданы `playerRefId` и `nickname`, сервис проверяет, что ник соответствует текущему `Player.nickname` найденного игрока. Это не позволяет связать игрока с чужим или устаревшим ником.

Пока frontend не передаёт `playerRefId`, его отсутствие не является ошибкой: сервис игры разрешает игрока по нику или создаёт новую запись. Когда frontend начнёт передавать идентификатор, backend продолжит принимать оба варианта до отдельного решения об ужесточении HTTP-контрактов.

MongoDB-доступ остаётся в `PlayersRepository` / `PlayersService`. Контроллеры конкретных игр и Quiz Events только валидируют вход и вызывают сервис своей игры; игровые engines не обращаются к базе и не создают игроков самостоятельно.

Целевой поток:

```text
Game Controller / Quiz Event Controller → Game Service → PlayersService.resolveOrCreate → Engine → Repository
```

Игровые engines получают уже подготовленные объекты участников с обязательным `playerRefId`. Они должны отклонять повторное добавление одного `playerRefId` в ту же партию, даже если пользователь указал разные алиасы этого игрока.

Lotto, Journey и Battleships не должны обращаться к `PlayersRepository` напрямую: их services вызывают `PlayersService.resolveOrCreate`, затем передают результат в engine. В Lotto и Journey дубликаты по nickname и `playerRefId` запрещены; Battleships хранит одну identity на уровне игры.

`PlayerReferencesRepository` уже ищет ссылки по `playerRefId` в `journey_games.stateV2.players`, `lotto_games.players`, `lotto_bingo_games.players`, корневом поле `battleships_games.playerRefId` и всех трёх местах Quiz Event. Он остаётся защитой legacy-данных и инструментом аудита, но не является race-safe механизмом физического удаления.

## План реализации Quiz Events

### Границы rollout

- Изменения выполняются только в backend. Текущий frontend продолжает передавать из чата `{ playerName, selectedMessageId }`.
- Работа с историей начинается с локальной базы. После успешных local `dry-run` и `--apply` production-миграция выполняется оператором отдельной командой; этот rollout не запускает её автоматически.
- `playerRefId` не включается в публичные Quiz Event DTO: frontend по-прежнему видит ник-снимок, сообщения, рейтинг, награды и summary в прежней форме.

### 1. Хранение ссылки

Для каждого выбранного правильного ответа сохраняются оба значения:

```ts
{
  playerName: string;      // снимок отправителя сообщения из чата
  playerRefId?: string;    // players._id, временно optional для старых событий
  selectedMessageId: string;
}
```

`playerRefId` является первичным источником идентичности участника. `playerName` остаётся неизменяемым историческим снимком и не заменяется текущим `Player.nickname`.

Ссылку необходимо также денормализованно сохранить в уже существующих производных результатах:

- `questions[].awards[].playerRefId` — копия ссылки получателя из выбранного ответа;
- `summary.players[].playerRefId` — ссылка игрока строки агрегированного summary.

Это не новые независимые источники истины: при создании/изменении результата они всегда производятся из `selectedAnswers`. Для legacy-read поля остаются optional.

### 2. Разрешение новой identity

Поток сохранения результата вопроса:

```text
QuizEventsController
  → QuizEventsService
    → QuizEventEngine.validateSelectionInputs (чистая проверка чата)
    → PlayersService.resolveOrCreate
    → QuizEventEngine.saveQuestionResult
    → QuizEventsRepository
```

1. HTTP-schema принимает необязательное `playerRefId?: string | null` наряду с текущими полями, поэтому frontend не требует изменений.
2. `QuizEventsService` до обращения к PlayersService выполняет чистую проверку: выбранное сообщение существует, принадлежит указанному нику, а сообщения и игроки не дублируются. Это исключает создание `Player` по невалидному запросу.
3. Затем сервис вызывает `PlayersService.resolveOrCreate(actor, projectId, { nickname: playerName, playerRefId })` для каждого выбранного ответа.
4. В engine передаются уже разрешённые selections с обязательным `playerRefId`; исходный `playerName` сохраняется как снимок и не подменяется ответом PlayersService.
5. Engine остаётся чистым: он не импортирует `PlayersService`, не обращается к MongoDB и не создаёт Player самостоятельно.

Если один `playerRefId` пришёл под двумя никами в одном результате, engine отклоняет результат так же, как и повторный `playerName`.

### 3. Правила наград и summary

- `QuizAnswerRanker` переносит `playerRefId` из selected answer во внутренний ranked answer.
- `QuizAwardCalculator` копирует его в award.
- При `limitOneBonusPerPlayer: true` набор уже получивших бонус строится по `playerRefId`; fallback на `playerName` нужен лишь для старых документов без ссылки.
- `QuizEventSummaryCalculator` группирует по `playerRefId`; fallback-ключ старого документа — нормализованный технический ключ от `playerName`. В видимую строку summary записываются и ссылка, и первый исторический `playerName`.
- Пересчёт результата вопроса, смена conducted order и пересборка summary используют тот же поток и не должны заново искать или создавать игроков.

### 4. Read models и поиск для будущего DELETE Player

- `QuizEventReadModelFactory` строит явные публичные `ranking`, `awards` и `summary`, исключая внутренний `playerRefId` на каждом уровне.
- `PlayerReferencesRepository` ищет Quiz Event по ссылкам в `questions.selectedAnswers`, `questions.awards` и `summary.players`, а fallback-поиск по историческому нику оставляется для неперенесённых событий.
- Аудит ссылок и служебный скрипт очистки игроков расширяются на все три места хранения Quiz Events.

### 5. Миграция существующих Quiz Events

Создаётся офлайн-скрипт `db:migrate:quiz-event-player-refs` с `dry-run` по умолчанию и явным `--apply`. Для целевого окружения используются отдельные команды `:local` и `:prod`.

Для strict all-or-nothing записи MongoDB должна работать в replica set: local `docker-compose.mongo.yml` поднимает одноузловой `rs0` и одноразово инициализирует его при старте. Скрипт не запускает контейнеры и не выполняет миграцию автоматически.

Для каждого event скрипт:

1. Ищет Player по `projectId` и текущему `nicknameKey` снимка; не использует aliases и не создаёт Player.
2. Добавляет resolved `playerRefId` в `selectedAnswers`.
3. Копирует ссылку в award по `selectedMessageId`, без пересчёта reward pool, позиции или суммы награды.
4. Добавляет ссылку в summary только если для его `playerName` найден ровно один resolved ref среди selected answers; несколько refs считаются неоднозначностью.
5. Не перезаписывает существующий отличающийся ref: фиксирует conflict и прекращает `--apply`.
6. Сохраняет все подходящие документы одной MongoDB-транзакцией; каждый update атомарно проверяет `{ _id, projectId, revision }`, обновляет `updatedAt` и увеличивает `revision`.

В отчёте должны быть `eventsScanned`, `eventsToUpdate`, количество добавляемых ссылок по каждому из трёх мест, `alreadyLinked`, `unresolved` и `conflicts`.

Порядок проверки: local dry-run → local `--apply` при нулевых конфликтах → повторный local dry-run → production dry-run → production `--apply` при нулевых конфликтах → повторный production dry-run. Production-команды запускает оператор после свежего полного backup.

### 6. Тесты и критерии приёмки

- Сервис создаёт или разрешает Player из ника чата, а engine получает подготовленную identity.
- Невалидный `selectedMessageId` или ник не создаёт Player.
- В новом сохранённом результате один ref одинаково записан в selected answer, award и summary.
- Награда `limitOneBonusPerPlayer` ограничивается по `Player._id`, а legacy-документы сохраняют fallback по нику.
- Один ref нельзя выбрать дважды в вопросе.
- Public Quiz Event JSON не содержит `playerRefId`.
- Миграция не меняет суммы/состав наград, создаёт ссылки только в local DB и корректно сообщает unresolved/conflicts.

## Этап 4. Завершить rollout

После подключения Quiz Events и, при необходимости, успешных миграций импортированных старых игр:

1. Сохранить обязательный `playerRefId` для всех новых игровых сущностей и входов engines; это уже сделано для Lotto Bingo, Lotto, Journey и Battleships.
2. Сохранить tolerant-read только для backup до их отдельного импорта.
3. Заменить временный single-operator `DELETE /players/:playerId` на lifecycle текущих ссылок, безопасный при конкурентных мутациях:
   - добавить Player поле-счётчик, например `activeGameReferences`; это количество текущих уникальных `(Player, game/Event)` ссылок, а не историческое участие и не количество Quiz selections/awards;
   - каждая операция, добавляющая или убирающая `playerRefId`, в одной MongoDB-транзакции сохраняет game/Event и применяет diff уникальных refs к Player-счётчикам;
   - для Quiz Event diff вычисляется из полного previous/next Event, поэтому несколько ответов одного Player в одном Event учитываются один раз;
   - удаление Player — условная транзакционная операция только при `activeGameReferences: 0`; операция, одновременно создающая ссылку, пишет тот же Player и не может оставить ссылку на удалённого Player;
   - отдельная миграция строит начальные счётчики по текущим сохранённым ссылкам всех игр и Quiz Events; `PlayerReferencesRepository` остаётся audit/fallback для legacy, а не источником конкурентной целостности.
4. Добавить проверки и тесты на:
   - совпадение `projectId` игрока и игры;
   - создание нового игрока по неизвестному нику;
   - создание нового игрока при нике, который совпадает только с историческим алиасом другого `Player`;
   - запрет одного `playerRefId` дважды в одной партии;
   - корректное восстановление истории после смены ника.
   - удаление Player после удаления единственной тестовой игры/Event;
   - запрет удаления при хотя бы одной текущей ссылке;
   - конкурентные создание ссылки и удаление Player без orphan references.

## Критерий готовности

- Все существующие игровые участники имеют `playerRefId` или отражены в явном отчёте исключений; для Lotto, Journey и Battleships сейчас сохранённых игр нет.
- Все новые партии и новые участники получают `playerRefId` до вызова игрового engine.
- Аналитика может агрегировать участие, победы и награды по `Player._id` внутри одного проекта.
- Ники остаются историческими снимками и не меняются при редактировании `Player.nickname`.
- После rollout lifecycle Player удаляется тогда и только тогда, когда `activeGameReferences` равно нулю; удалённые games/Events корректно освобождают их текущие ссылки.
